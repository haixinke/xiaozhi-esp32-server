# 小纸条奖励与游戏星星结算 (Daily Note Rewards and Game Star Settlement)

Status: ready-for-agent

## Problem Statement

用户打开小纸条后需要获得星星并存入用户级星星罐，连续每天打开可递增奖励。其他游戏需要按配置赚取或消耗星星，但现有后端只有游戏配置和钱包基础能力，尚未接通小纸条发奖，也没有可复用的游戏奖扣方法。

## Solution

仅改造后端服务：接通现有小纸条打开接口，新增统一的每日奖励能力和标准游戏扣费方法。每日奖励表负责领取资格及小纸条连续计算；现有星星账户和流水负责余额与收支。免费游戏直接跳过，不创建独立游戏结算表，不预设游戏完成事件单号字段。

## User Stories

1. As a 小程序用户, I want to 当天首次打开小纸条获得11颗起的星星, so that 星星自动存入我的星星罐。
2. As a 小程序用户, I want to 连续每天打开小纸条时奖励每天增加1颗、最多17颗, so that 连续参与获得更多奖励。
3. As a 小程序用户, I want to 中断后从11颗重新开始, so that 连续奖励规则明确。
4. As a 小程序用户, I want to 切换宠物、设备或重复打开时不重复发奖, so that 每天资格跨端一致。
5. As a 小程序用户, I want to 每种奖励游戏每天首次成功完成时获得配置的固定星星, so that 不同游戏各有一次赚星星机会。
6. As a 小程序用户, I want to 奖励游戏中途退出或失败不占机会, so that 后续成功完成仍能领奖。
7. As a 小程序用户, I want to 打开小纸条和完成推荐游戏分别获得奖励, so that 两种资格互不影响。
8. As a 小程序用户, I want to 消费型游戏每局开始前扣费且余额不足不能开始, so that 不会产生负余额。
9. As a 小程序用户, I want to 同一局扣费请求重试不重复扣款, so that 网络重试不会多花星星。
10. As an 运营人员, I want to 游戏只能配置奖励或消费、也可配置双零免费, so that 配置含义清晰。
11. As a 后端维护者, I want to 其他游戏复用标准内部奖扣方法, so that 后续接入不重复实现每日资格、入账与扣费防重复逻辑。
12. As a 后端维护者, I want to 奖励记录与钱包变动事务一致, so that 失败重试不会漏发或重复入账。

## Implementation Decisions

### 已确认范围与规则

- 仅改造后端服务，不修改蛋宝宝小程序。
- 小纸条奖励存入用户的星星罐，每用户每自然日最多一次；重复打开、切换宠物或设备、网络重试不重复发奖，也不增加连续天数。
- 自然日采用北京时间（Asia/Shanghai），每天零点换日。
- 首次成功领取 11 颗；昨天成功领取则今天增加 1 颗，最高 17 颗；达到上限后连续领取保持 17 颗；中断后恢复 11 颗。
- 上线后的首次成功领取从 11 颗开始；历史打开记录不参与连续计算，也不补发。
- 其他游戏奖励为游戏管理中定义的固定数量，不使用连续累加规则。
- 其他游戏按每用户、每种游戏（游戏类型）、北京时间每自然日各一次计算赚星星机会，切换宠物或设备不增加机会；该限制由本期标准内部发奖方法负责执行。
- 其他游戏在当天首次成功完成时获得固定奖励，中途退出或失败不占机会；完成事实由后续接入的游戏业务验证，再调用标准内部方法。
- 提炼标准的赚星星方法，供不同游戏类型使用。
- 标准游戏接口同时覆盖消耗星星的游戏，按游戏管理中的消耗数量每局扣费，不受每日首次奖励限制。
- 消费型游戏在开始前扣费，余额不足不能开始；同一局的重复请求只扣一次。
- 游戏奖励与消费互斥：`earnStars` 与 `consumeStars` 不得同时大于零，此约束由后端配置校验负责执行。
- 奖励与消费均为零时，允许作为免费无奖励游戏，不扣不发，也不占当天奖励机会。
- 免费游戏不记录星星业务数据；当天已领取后的额外游玩也不新增奖励记录或资金流水。
- 游戏不存在或停用时，拒绝新结算；已成功结算的同一业务请求重试返回原结果，不受后续配置变动或停用影响。
- 本期不提供退款能力；扣费成功后的异常交由人工处理。扣费事务自身失败则回滚，不产生成功扣费。
- 上线当天已经打开过小纸条的用户不补发，从次日首次有效打开开始领 11 颗；当天尚未打开的用户可领 11 颗。
- 本期沿用现有小纸条打开接口触发奖励并保持接口兼容；客户端是否已调用该接口属于接入前提，不在本期修改范围内。
- 其他游戏本期提供标准内部星星结算方法，涵盖奖励与扣费能力，不新增通用游戏完成接口，不接通具体游戏完成事件。
- 打开小纸条与完成推荐游戏是两份独立奖励，可分别获得；小纸条有当日内容且打开请求有效时，不要求存在可用推荐游戏。

### 现有实现事实

- 小纸条已有 `POST /app/daily-note/opened`，无请求体，当前返回空数据，仅记录用户当天首次打开状态，尚未发放星星。
- 小纸条已使用北京时间时钟；打开记录以用户和日期唯一。
- 小纸条今日查询在已打开、无当日内容或无可用入口游戏时返回空；打开接口本身不要求存在可用游戏。
- 星星模块已有内部 `earn`、`consume` 方法，以用户、业务类型和业务单号防止重复入账或扣款；扣款具备余额不足校验，对外仅提供余额和流水查询。
- 游戏配置已有固定奖励字段 `earnStars` 和消耗字段 `consumeStars`，均可为非负整数；应用接口目前只有列表查询，尚无通用游戏完成或星星结算链路。
- 仓库中的蛋宝宝小程序尚未找到调用小纸条或星星接口的代码；仅修改后端无法保证现有客户端点击会触发请求。
- 星星罐与业务状态保持分离，参照 ADR 0008、0009。

### 奖励计算示例

- 小纸条连续领取第 1 至第 8 天：11、12、13、14、15、16、17、17 颗；漏掉一天后再次领取为 11 颗。
- 同一天打开小纸条多次或切换宠物、设备，只领取一份小纸条奖励。
- 同一天首次成功完成“一起画”和“听你说”，各按对应游戏配置获得一份固定奖励；再次完成其中任一游戏均不增加当天奖励。
- 同一天先中途退出游戏，随后成功完成，仍可获得该游戏当天的首次奖励。
- 消费型游戏每局配置扣 5 颗时，当天玩三局共扣 15 颗，同一局请求重试不额外扣费；余额不足则该局不能开始。
- 免费无奖励游戏成功完成后当天调高奖励，后续首次符合奖励条件的成功完成仍有当天领奖资格。

### 服务边界

- 保留现有星星罐作为余额和流水的唯一入账入口，不把连续奖励规则加入钱包。
- 提供统一的每日赚星星服务：负责用户与奖励来源的每日资格、防止重复发奖，以及调用钱包入账；小纸条与固定游戏分别计算金额。
- 小纸条使用独立奖励来源；游戏奖励按游戏类型区分来源。小纸条和推荐游戏互不占用对方机会。
- 领取状态与历史打开状态区分，连续计算仅使用新规则下的成功领取记录；保留原有打开记录及其查询语义。
- 小纸条打开接口编排打开状态与每日奖励，事务内同时提交；接口地址、请求体和成功响应结构保持兼容。
- 固定游戏方法按后端游戏管理配置取金额，不接收客户端指定奖励数量；本期无新增游戏完成 HTTP 接口。
- 不修改现有游戏每日可玩次数及其按设备配置的含义；每日奖励限制由统一服务独立执行。
- 标准游戏结算入口区分奖励与扣费，避免将每日首次奖励限制套用到消费场景，具体职责见下文。
- 游戏扣费复用钱包原子扣减和流水，金额读取后端配置，同一笔业务重试不重复扣款，余额不足时拒绝扣款。
- 配置新增与编辑均校验奖励和消费互斥；上线前需只读核查存量配置是否冲突，发现冲突应报告并明确处理，不静默改写运营配置。

### 标准内部接口职责

以下为职责定义，方法命名在实现时遵循项目现有规范；本期不暴露客户端可直接指定金额的星星写接口。

| 入口 | 调用时机 | 金额规则 | 防重复边界 |
| --- | --- | --- | --- |
| 小纸条奖励 | 现有小纸条打开接口内 | 首次 11，连续每日 +1，最高 17，中断重置 | 用户 + 小纸条奖励来源 + 北京日期 |
| 游戏奖励 | 游戏业务验证成功完成后 | 对应游戏当前 `earnStars` | 用户 + 游戏类型 + 北京日期 |
| 游戏扣费 | 游戏业务允许开始前 | 对应游戏当前 `consumeStars` | 用户 + 游戏类型 + 同一局业务单号 |

- 游戏奖励方法接受用户、游戏类型及后端业务完成凭据；游戏扣费方法接受用户、游戏类型及后端生成或验证的局次业务单号。调用方不能通过更换请求号绕过每日奖励限制。
- 游戏完成事实与局次身份由接入业务保证，本期不创建通用游戏开局/完成 HTTP 接口，也不为未接入游戏实现完整局次状态机。
- 小纸条与游戏奖励共用每日资格与入账机制，金额策略分别处理；消费入口使用按局防重复机制，复用同一个钱包扣减能力。
- 返回结构明确区分本次结算成功、已结算、无需星星变动；已结算返回首次结算的数量与流水标识，不重新按配置计算。余额不足、配置无效等失败应显式返回业务错误。
- 对奖励型游戏调用扣费入口、对消费型游戏调用奖励入口时，不发生星星变动、不占奖励资格；纯免费游戏同样无星星变动。

### 数据与事务边界

- 每日奖励记录属于奖励业务，记录用户、奖励来源（小纸条或游戏类型）、北京时间日期、实际数量以及关联流水；以用户、来源和日期唯一约束防止重复领取。
- 小纸条连续奖励以新规则下昨天的成功奖励为依据：昨天有领取则 `min(昨天数量 + 1, 17)`，否则 11；不需要回溯完整历史天数。
- 对同一用户的奖励结算在数据库事务中串行化，确定领取日期和连续金额后写入领取记录并调用钱包；使用数据库唯一约束与事务保障跨设备、并发及日界附近的正确性。
- 首次打开记录、每日领取记录和钱包流水原子提交；发星失败不留下已打开但未领奖的新记录。已存在的历史打开记录继续按上线规则跳过。
- 游戏配置与实际金额在首次成功结算时确定并保留结果；后续防重复查询先于当前配置校验，保证游戏修改或停用后重试仍返回原结果。
- 钱包流水以不同业务类型区分小纸条奖励、游戏奖励、游戏扣费，业务单号包含必要的来源信息，避免不同游戏或奖扣场景互相碰撞；钱包只保存资金事实，不承载游戏生命周期。
- 零星星操作直接跳过，不调用钱包、不新增星星业务记录，不占奖励资格；不保留零金额请求快照。已发生正数奖励或实际扣款的请求重试返回原记录。

### 交付范围

- 修改后端 Java 服务、必要的数据库迁移、测试与本设计相关文档。
- 接通小纸条现有打开接口；提供其他游戏的标准内部奖励和扣费方法。
- 游戏配置保存时增加奖扣互斥校验，并在结算时防御性校验存量冲突。
- 不修改蛋宝宝小程序和智控台前端，不接入具体游戏完成链路，不新增退款能力，不调整每日可玩次数的原有含义。

### 表结构方案

仅新增每日奖励记录一张表，复用五张现有表。免费游戏直接跳过，不记录零金额结算；当天已领取时读取原奖励记录即可，不记录后续未获奖励的游玩。本期不建独立游戏结算表。以下 DDL 为已确认的表设计；实现时通过 Liquibase 新增 changeSet 和 SQL 文件，不修改已有迁移。

| 表 | 作用 | 本期结构变更 |
| --- | --- | --- |
| `ai_star_daily_reward` | 每日奖励资格及实际奖励记录 | 新增 |
| `ai_star_account` | 用户余额 | 无 |
| `ai_star_transaction` | 所有星星收支流水 | 无，扩展业务类型枚举及对应说明 |
| `ai_daily_note_opened` | 用户每天首次打开状态 | 无，不回填历史奖励 |
| `ai_daily_note` | 每日纸条内容 | 无 |
| `ai_game` | 游戏奖励、消费及可玩次数配置 | 不新增列，后端增加奖扣互斥校验 |

```sql
CREATE TABLE `ai_star_daily_reward` (
  `id` BIGINT NOT NULL COMMENT '主键ID(雪花)',
  `user_id` BIGINT NOT NULL COMMENT '用户ID',
  `source_type` VARCHAR(16) NOT NULL COMMENT '奖励来源类型: DAILY_NOTE/GAME',
  `source_key` VARCHAR(64) NOT NULL COMMENT 'DAILY_NOTE固定为DAILY_NOTE; GAME为游戏类型code',
  `reward_date` DATE NOT NULL COMMENT '北京时间领取自然日',
  `amount` BIGINT NOT NULL COMMENT '本次实际奖励数量，必须大于0',
  `star_transaction_id` BIGINT NOT NULL COMMENT '关联星星入账流水ID',
  `create_date` DATETIME NOT NULL COMMENT '领取记录创建时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_star_daily_reward_user_source_date`
    (`user_id`, `source_type`, `source_key`, `reward_date`),
  UNIQUE KEY `uk_star_daily_reward_transaction` (`star_transaction_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='每日星星奖励记录';
```

- 每日唯一索引保证小纸条一天一次、每种游戏各一天一次，也支持按完整来源与昨天日期查询小纸条奖励；当前无按日期扫描全量用户需求，不另加日期单列索引。
- `amount` 是成功结算快照，不随游戏配置变动重算。仅正数成功奖励落表，零奖励不落表。
- 不保存连续天数或可变状态：小纸条读取昨天的成功奖励金额即可计算今天数量；失败整体回滚，表中无半成功记录。
- 不加入宠物、设备、小纸条内容 ID 或游戏配置行 ID：资格按用户、来源和日期定义，内容删除或配置重建不重置当天已领取资格。
- `star_transaction_id` 与星星流水逻辑关联，不建物理外键；业务事务保证一条奖励对应一条入账流水。先分配奖励记录 ID，用该 ID 作为钱包业务单号；钱包入账后获取流水 ID，再写奖励记录，整个过程在同一事务中串行执行。
- 游戏类型 code 使用后端校验后的规范值，字符串比较与现有字典、游戏配置规则保持一致；不得因大小写差异形成两份资格。
- 本期不新增游戏完成事件单号字段。游戏完成事实、时效和旧事件重试由后续接入业务结合实际完成记录验证；每日唯一键只保证当天一次，不单独承担跨日旧完成事件识别。

消费不写每日奖励表，直接复用星星流水的 `(user_id, biz_type, ref_id)` 唯一约束。同一局扣费先查原流水，存在则返回原扣款金额，不再读取新费用。业务类型区分小纸条奖励、游戏奖励及游戏扣费；奖励使用每日奖励记录 ID 作为钱包业务单号，扣费单号由后端对规范序列化的游戏类型与可信局次单号计算 SHA-256，64位十六进制串适配现有 `ref_id VARCHAR(64)`，避免直接拼接产生超长或歧义。

当天已领取后的额外游玩直接返回当天奖励机会已使用，不产生新流水；当天第一次奖励的流水始终存在。返回时必须区分原奖励数量与本次新增数量（为0），不得误报重复发奖。游戏不存在、停用、余额不足等失败不写成功记录。

奖励并发不能只依赖先查后写：实现时先确保用户账户存在，再在同一事务中锁定该用户账户行，使用当前读读取奖励与流水，确定业务日期、计算金额并入账。当前 DAO 需补充账户行锁查询；不得依赖可重复读事务中锁等待前的旧快照。重复请求在锁内读到原结果；新请求以取得锁后的北京时间归属日期。扣费仍须原子条件更新余额，防止余额不足时扣款。每日奖励记录与钱包流水在同一事务提交；免费游戏应在无需创建账户或资金记录的路径直接跳过。

## Testing Decisions

- 先写失败测试再实现，以公开 Service 方法、HTTP 契约及真实数据库状态验证外部行为，相关服务有效覆盖率目标80%以上。
- 使用可替换时钟验证北京时间日界；事务回滚、并发重复发奖和重复扣费需覆盖数据库集成测试，测试数据独立并清理，不修改运营数据。

### 验收范围

- 首次 11 颗、连续递增、17 颗封顶、中断重置、北京时间跨日。
- 同用户跨设备和宠物重复请求、并发请求均只入账一次。
- 历史记录不参与连续计算且不补发；上线当天已打开用户次日首次领取 11 颗，未打开用户当天可领 11 颗。
- 无当日纸条不发奖；有当日纸条但无可用推荐游戏仍可经有效打开请求领奖。
- 游戏按用户、游戏类型、日期独立限奖，金额取配置，重复成功完成不再发奖。
- 业务状态与钱包入账任一步骤失败时整体回滚，重试可重新领取。
- 游戏扣费金额取配置，余额不足不产生成功扣款；重复请求和并发重试不重复扣款。
- 配置校验拒绝同时赚取和消耗星星的游戏。
- 游戏修改或停用后，已成功结算请求重试返回原结果；不存在或停用的游戏不接受新结算。
- 免费无奖励游戏不新增星星业务数据、不占每日奖励资格；当天已领奖后的额外游玩不新增奖励记录和流水。
- 既有接口兼容，蛋宝宝小程序代码无改动。

## Out of Scope

- 蛋宝宝小程序和智控台前端改动。
- 具体游戏玩法、游戏开局和完成 HTTP 接口、通用游戏局次状态机。
- 其他游戏完成事件的实际接入；本期仅提供内部标准奖扣方法。
- 退款能力；已成功扣费后的异常人工处理。
- 免费游戏及当天重复游玩未获奖的额外星星记录、独立游戏结算表。
- 游戏完成事件单号字段及基于该字段的通用跨日重放识别。
- 现有每日可玩次数的计数或语义变更、历史奖励补发、小程序真实环境验证。

## Further Notes

- 奖励数量和业务身份由后端决定。
- 同一次小纸条领取的打开状态、奖励状态和钱包入账需要保持事务一致；失败重试不得造成漏发或重复入账。
- 历史打开记录与新奖励记录需要可区分，避免历史数据进入连续计算。
- 后续游戏奖励需要绑定后端可验证的业务事件，不能依赖客户端任意生成的单号防重。
- 每日赚星星资格与现有按设备配置的每日可玩次数分开建模，不因允许多次游玩而重复发奖。
- 设计与表结构已确认，本 spec 尚未实现；不要把文档状态理解为代码或数据库变更已经完成。
