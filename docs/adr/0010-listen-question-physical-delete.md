# 0010. 听你说题库物理删除：不设 deleted 列，为例外于 0006 软删惯例的有意决策

- 状态：已接受
- 日期：2026-10-28

## 背景

ADR 0006 确立了仓库的删除惯例：用户侧数据（宠物实例）采用逻辑删除（`deleted_at` 时间戳标记 + 手动过滤），以保留审计与人工恢复能力。听你说题库（`ai_listen_group` / `ai_listen_question`）落地时需要决定沿用还是例外。

题库与宠物场景的关键差异：

1. **无用户侧历史记录关联**：答题记录本期不存在（「听你说」游戏本身未立项，取题接口未暴露），题目是纯运营内容，删除后没有任何用户数据会失去指向——软删要保护的"历史记录不断链"对象不存在。
2. **低频运营操作**：题目维护是后台运营行为（新增、改错字、整组下线），非用户高频路径；误删风险由前端删除二次确认兜底（确认文案明示"物理删除不可恢复"）。
3. **软删有实际成本**：若加 `deleted` 列，所有题库查询要加过滤谓词；导入判重 SQL（同大类组名唯一、同组题干唯一的库内比对）要把"已删除的同名行"排除在冲突判定外，徒增复杂度。

## 决策

1. **`ai_listen_group` / `ai_listen_question` 不设 `deleted` 列，删除即物理 DELETE**：单题删除、整组删除（级联删组内题目）、整组保存 diff 中缺失题目的移除，均为物理删除。
2. **唯一约束直接落在业务列上**：`(category_code, name)` 与 `(group_id, text)` 联合唯一约束不需要像 0006 那样为软删改造（无"删除后同名再建撞键"问题——物理删除后行已不存在）。
3. **前端二次确认兜底**：删除操作在智控台弹确认框，文案明示不可恢复；接口侧不做回收站/恢复能力。

## 否决的替代方案

- **沿用 0006 逻辑删除（`deleted_at` 标记 + 手动过滤）**：保护对象（用户侧历史关联）不存在，是纯成本——每个读取点加过滤谓词、导入判重 SQL 需排除已删行、唯一索引需为软删改造。YAGNI。
- **回收站/延迟物理删除**：运营低频场景下引入额外表与清理任务，复杂度远超收益；二次确认已足够兜底。

## 后果

- 删除不可恢复：误删需重新导入 JSON 或手工补录；前端确认文案必须明示（已在删除确认中落实）。
- 导入判重、唯一约束、查询 SQL 均不含 `deleted` 过滤谓词，实现与 ADR 0006 的宠物模块相比更简单。
- 若未来引入答题记录等用户侧关联数据（「听你说」游戏落地时），需重新评估是否改回逻辑删除——届时删除题目会使历史答题记录失去题干指向。
