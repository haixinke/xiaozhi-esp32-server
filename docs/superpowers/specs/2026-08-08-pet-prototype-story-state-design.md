# 宠物原型共享故事状态后端设计

- 日期：2026-08-08
- 范围：`main/manager-api`，不包含 manager-web 和蛋宝宝小程序改造
- 依赖：现有 `storyengine` 大场景、小场景、动作和动作图片基础数据

## 1. 背景与目标

现有故事引擎只管理故事基础数据：大场景、小场景、各时段小场景出现概率、动作、动作持续时间以及按宠物原型和图片时段配置的动作图片。它尚未维护运行中的故事状态。

本设计增加后端故事运行时：每小时为平台支持的每种宠物原型检查并推进一次共享故事状态。当前固定支持“锦鲤”和“玉兔”，因此实时表最多保存两条有效记录。同一原型的所有独立宠物共享当前状态和历史；查询单只宠物时，后端先解析其原型，再读取该原型的共享记录。

目标包括：

- 按当前时段和小场景概率生成宠物原型的共享故事状态。
- 遵守动作持续时间，动作到期前不切换。
- 成功切换时原子归档旧状态，并保存不可变内容快照。
- 在多实例部署下保证每个原型、每个整点时槽最多完成一次有效计算。
- 提供按宠物 ID 查询共享当前状态和分页历史的后端接口。
- 只处理后端，不修改小程序展示或调用逻辑。

## 2. 已确认的业务规则

- 计算维度是宠物原型，不是单只宠物。锦鲤共享一条实时状态，玉兔共享另一条实时状态。
- 支持的原型由后端明确维护，当前固定为“锦鲤、玉兔”。即使某种原型暂时没有已破壳宠物，也持续维护该原型状态。
- 定时任务每小时整点执行一次，统一使用 `Asia/Shanghai` 时区。
- 每小时都会检查两个原型，但只有状态未初始化或动作到期时才尝试生成故事；动作未到期时保持不变。
- 普通切换使用小场景配置的真实百分比。各时段权重合计小于 100% 时，剩余概率表示“保持原状态”，下一小时再尝试。
- 首次初始化没有原状态可保持，因此在配置完整的有效候选之间按相对权重选择，尽可能保证产生初始状态。
- 小场景命中后，从具有匹配图片的启用动作中等概率选择动作。
- 动作持续时间在 `duration_min` 到 `duration_max` 之间按整数小时随机选择，包含上下限。
- 同一动作、原型和图片时段下，多张图片等概率选择；图片配文以 `|` 分隔，从非空配文中随机选择一条。
- 图片和配文选定后，在整个状态持续期间保持不变。
- 再次选中相同场景或动作仍视为一个新状态，正常归档旧状态并重新选择图片、配文和持续时间。
- 当前基础配置被禁用、改名或删除时，不立即中断已经运行的状态；当前状态依靠快照持续到下一次成功切换。
- 服务停机期间不补演多个故事状态。恢复后的下一次任务只生成一个从实际切换时间开始的新状态。
- 未破壳宠物不能通过查询接口看到共享故事。当前状态返回空，历史返回空分页。

## 3. 方案选择

采用“独立当前状态表 + 只追加历史表”。

### 3.1 采用方案

- `ai_pet_story_state`：每种宠物原型一条当前状态，`pet_prototype` 唯一。
- `ai_pet_story_history`：成功切换前复制旧状态快照，只追加，不修改历史。

该方案使当前状态查询、到期判断、原型级行锁和历史分页保持简单。当前表与历史表存在有意的字段重复，用于保证基础配置变化后仍能正确展示当时内容。

### 3.2 未采用方案

- 单一流水表加 `is_current`：保证每种原型只有一条当前记录、并发切换和当前查询都更复杂。
- 将当前字段写入 `ai_pet`：会按宠物实例重复存储同一个原型状态，并把宠物档案与故事运行态错误耦合。
- 为每只宠物独立计算：计算量随宠物数量增长，也不符合“同原型共享实时故事”的产品规则。

## 4. 架构与组件边界

### 4.1 `StoryStateSelector`

纯领域选择组件，输入宠物原型、当前时间和候选基础数据，输出完整候选状态或明确的未命中结果。它负责：

- 权重时段和图片时段映射。
- 首次初始化的相对权重选择。
- 普通切换的 1～100 概率选择及剩余概率处理。
- 启用状态和配置完整性过滤。
- 动作、图片、配文和持续时间选择。

该组件不负责事务或数据库写入。时钟与随机数生成器可替换，以支持确定性测试。

### 4.2 `PrototypeStoryStateService`

负责一个宠物原型的一次整点检查：

- 锁定并读取原型当前状态。
- 执行整点时槽幂等判断。
- 调用选择组件。
- 成功切换时归档旧状态并写入新状态。
- 未命中、动作未到期或配置不完整时只更新本时槽检查标记。

### 4.3 `PrototypeStoryStateRefreshTask`

使用 Spring `@Scheduled`，cron 为 `0 0 * * * ?`，时区为 `Asia/Shanghai`。任务只遍历固定支持列表“锦鲤、玉兔”，每个原型使用独立短事务。一个原型失败不影响另一个原型。

### 4.4 `PetStoryController`

提供用户态只读接口。控制器接收宠物 ID，沿用现有宠物归属校验，确认已破壳后读取 `PetEntity.prototype`，再查询原型共享状态。它不承担状态生成逻辑，也不加入现有故事内容管理控制器。

### 4.5 持久层

新增当前状态和历史记录各自的实体、MyBatis-Plus DAO 与查询服务。现有故事基础数据 CRUD 服务保持职责不变。

## 5. 数据模型

### 5.1 `ai_pet_story_state`

每种支持的宠物原型一条记录。迁移时预置锦鲤、玉兔两条 `UNINITIALIZED` 行，保证首次运行和多实例初始化也能使用稳定的行锁。

| 列 | 说明 |
|---|---|
| `id` | UUID 主键 |
| `pet_prototype` | 宠物原型，唯一且不可空 |
| `runtime_status` | `UNINITIALIZED` 或 `ACTIVE` |
| `big_scene_id` / `big_scene_name` | 大场景引用与名称快照 |
| `small_scene_id` / `small_scene_name` | 小场景引用与名称快照 |
| `action_id` / `action_name` | 动作引用与名称快照 |
| `action_image_id` | 选中的动作图片 ID |
| `weight_period` | `NIGHT`、`MORNING`、`AFTERNOON` 或 `EVENING` |
| `image_time_of_day` | `DAY`、`SUNSET` 或 `NIGHT` |
| `image_url` | 动作图片 URL 快照 |
| `caption` | 选中的单条配文快照，可空 |
| `duration_hours` | 本次随机生成的整数持续小时数 |
| `started_at` | 实际开始时间 |
| `expected_end_at` | 最早允许下次切换的时间 |
| `last_evaluated_hour` | 最近完成检查的整点时槽，多实例幂等字段 |
| `creator` / `create_date` / `updater` / `update_date` | 项目统一审计字段 |

`UNINITIALIZED` 行的故事快照字段允许为空；`ACTIVE` 行必须具有完整的场景、动作、图片和时间字段。数据库使用 `UNIQUE uk_pet_story_state_prototype(pet_prototype)` 保证每种原型最多一条当前状态。

当前任务始终按两个已知原型主键读取，不需要基于到期时间扫描大量状态，因此不额外建立到期扫描索引。

### 5.2 `ai_pet_story_history`

历史表只保存真正运行过的 `ACTIVE` 状态，不保存初始化占位记录。字段包含当前状态的全部故事快照，并增加：

| 列 | 说明 |
|---|---|
| `id` | 独立历史 UUID 主键 |
| `archived_at` | 被下一状态实际替换的时间 |

历史表使用 `INDEX idx_pet_story_history_prototype_started(pet_prototype, started_at, id)`，支持按原型稳定倒序分页。

### 5.3 快照与关联策略

两张新表保存基础记录 ID，也保存名称、图片 URL 和已选配文快照。查询状态与历史时不再关联基础表补齐展示内容。两张表不设置数据库外键，与现有 storyengine 表一致，并允许运营删除基础配置后保留历史可读性。

## 6. 时段与随机选择规则

### 6.1 时段映射

| `Asia/Shanghai` 时间 | 权重字段 | 图片时段 |
|---|---|---|
| 00:00～05:59 | `weight_night` | 黑夜 / `NIGHT` |
| 06:00～11:59 | `weight_morning` | 白天 / `DAY` |
| 12:00～17:59 | `weight_afternoon` | 白天 / `DAY` |
| 18:00～23:59 | `weight_evening` | 落日 / `SUNSET` |

### 6.2 首次初始化

1. 查询已启用大场景下所有已启用且当前权重大于零的小场景，并按 `sort_order, id` 固定顺序处理。
2. 排除没有启用动作或没有当前原型、图片时段匹配图片的小场景。
3. 在剩余候选间按相对权重随机选择，权重不要求合计为 100%。
4. 没有有效候选时保留 `UNINITIALIZED`，记录告警并等待下一小时。

### 6.3 普通切换

1. 对已启用大场景下的所有已启用小场景，按 `sort_order, id` 固定顺序和当前时段字段构建原始概率区间。
2. 生成 1～100 的随机整数。
3. 随机数超过已配置权重合计时，结果为“保持原状态”。
4. 命中的小场景没有有效动作或匹配图片时，本次计算视为配置失败并保持原状态，不重新抽取其他小场景，以免改变配置概率。
5. 从命中小场景下具有匹配图片的启用动作中等概率选择一个动作。
6. 从匹配当前原型和图片时段的图片中等概率选择一张。
7. 将 `captions` 按 `|` 分割、去除空白项后等概率选择一条；没有非空配文时 `caption` 为空。
8. 在动作持续时间上下限之间等概率选择整数小时。

基础管理服务正常情况下保证每个时段的全局启用权重合计不超过 100。运行时仍进行防御性校验：发现负权重、合计超过 100 或非法持续时间时，将本次结果视为配置失败并保持原状态，不按截断后的错误概率继续运行。

## 7. 状态流转

每个原型在当前整点时槽内按以下顺序处理：

1. 锁定 `ai_pet_story_state` 对应原型行。
2. 将 `Asia/Shanghai` 当前时间截断到整点得到时槽；如果 `last_evaluated_hour` 已等于该时槽，立即跳过。
3. 如果状态为 `ACTIVE` 且 `expected_end_at` 晚于当前时间，保持当前状态。
4. 如果状态为 `UNINITIALIZED`，执行首次初始化选择。
5. 如果状态为 `ACTIVE` 且已经到期，执行普通切换选择。
6. 首次初始化成功时更新占位行为 `ACTIVE`，不写历史。
7. 普通切换成功时，先复制旧状态到历史表，再用候选状态更新当前行。
8. 无论动作未到期、概率未命中还是配置不完整，只要本次检查正常完成，都更新 `last_evaluated_hour`。
9. `last_evaluated_hour`、历史插入和当前状态更新在同一事务提交。

新状态使用实际切换时间作为 `started_at`，并按随机持续小时数计算 `expected_end_at`。旧状态的 `archived_at` 使用实际被替换时间，因此在概率连续未命中时，实际持续时间可以超过原计划结束时间。

## 8. 多实例并发与事务

仅使用行锁不足以保证概率正确：一个实例未命中并保持旧状态后，另一个实例仍可能发现动作已到期并再次抽取。因此必须组合“原型行锁 + 整点时槽幂等”。

每个原型通过独立 `TransactionTemplate` 事务处理：

1. 使用 `SELECT ... FOR UPDATE` 锁定原型状态行。
2. 在锁内比较 `last_evaluated_hour` 和当前整点时槽。
3. 本时槽已经完成时直接跳过；否则执行状态检查和选择。
4. 正常完成后在同一事务更新 `last_evaluated_hour`。
5. 发生异常时整个事务回滚，包括时槽标记、历史归档和当前状态修改。

多个实例同时启动时，第一个实例完成并提交后，后获得锁的实例重新读取到相同时槽标记并跳过。第一个实例异常回滚时，标记不会保存，其他实例仍可在同一小时接手重试。

锦鲤和玉兔使用不同状态行，彼此不阻塞。不引入 Redis 分布式锁、Quartz 或 ShedLock；当前模型只有两个稳定锁目标，数据库行锁与事务已经提供足够且可验证的并发语义。

## 9. 查询接口

### 9.1 当前状态

```text
GET /pet/{id}/story-state
```

处理流程：

1. 获取当前登录用户。
2. 查询其名下指定宠物；不存在或不属于当前用户时沿用现有宠物接口错误语义。
3. 宠物未破壳时返回成功响应且 `data = null`。
4. 按宠物 `prototype` 查询共享当前状态。
5. 对应状态不存在或为 `UNINITIALIZED` 时返回成功响应且 `data = null`。
6. `ACTIVE` 时返回场景、动作、图片、配文、时段、持续小时数和起止时间快照。

### 9.2 故事历史

```text
GET /pet/{id}/story-history?page=<page>&limit=<limit>
```

接口沿用项目现有分页信封和参数约定。宠物未破壳时返回空分页。已破壳时按宠物原型查询共享历史，以 `started_at DESC, id DESC` 排序。同一原型的所有宠物看到相同历史。

本版本不提供管理员跨用户查询接口，不修改小程序调用。

## 10. 错误处理与可观测性

- 单个原型失败不影响另一个原型，失败原型由同一时槽的其他实例或下一小时自然重试。
- 状态切换任何一步失败时，历史和当前状态不得出现部分提交。
- 概率未命中是正常业务结果，不记录错误。
- 缺少启用场景、动作或匹配图片属于内容配置告警，保持原状态。
- 不可恢复的数据异常记录错误并回滚事务。
- 定时任务汇总日志记录时槽、原型、初始化数、切换数、保持数、跳过数和失败数。
- 日志不得包含用户 ID、宠物实例 ID、设备 ID、token 或其他敏感数据。

## 11. 测试与验收

随机逻辑使用可注入的 `Clock` 和随机数生成器，确保测试可重复。新增代码目标覆盖率不低于 80%。

### 11.1 选择器单元测试

- 四个权重时段及三个图片时段的边界映射。
- 首次初始化按有效候选相对权重选择。
- 普通切换命中各概率区间及剩余概率。
- 禁用的大场景、小场景和动作不会被选择。
- 缺少匹配原型或图片时段的图片时返回配置失败。
- 动作持续时间可以命中上下限。
- 图片和非空配文选择。
- 相同场景或动作再次命中仍产生完整新候选。

### 11.2 服务与事务测试

- `UNINITIALIZED` 首次初始化成功且不写历史。
- 首次初始化没有有效候选时保持占位状态。
- 动作未到期时不切换。
- 到期后概率未命中时不写历史、状态不变。
- 成功切换时历史归档和当前状态同时提交。
- 配置不完整时保持原状态并更新本时槽标记。
- 任一步异常时当前状态、历史和时槽标记全部回滚。
- 同一原型、同一时槽调用多次，只允许一次完成计算。
- 第一个实例异常回滚后，第二个实例能在同一时槽接手。
- 下一整点时槽可以重新计算。
- 锦鲤处理失败不阻断玉兔处理。

### 11.3 接口测试

- 不能跨用户读取其他用户宠物的故事数据。
- 未破壳宠物返回空状态和空历史。
- 同原型宠物读取相同状态及历史。
- 不同原型读取独立状态及历史。
- `UNINITIALIZED` 返回空状态。
- 历史分页排序稳定。

### 11.4 数据库验证

- Liquibase 从当前版本正常创建两张表并预置两个原型状态行。
- `pet_prototype` 唯一约束阻止重复当前记录。
- 历史联合索引存在且支持查询排序。
- 并发测试验证原型行锁和时槽幂等组合不会重复切换或重复归档。

## 12. 非目标

本次不包含：

- 小程序页面、接口调用或缓存改造。
- manager-web 当前状态或历史管理页面。
- 管理员跨用户查询接口。
- 单只宠物个性化故事状态。
- 动态新增宠物原型的运营配置；新增原型需要后端支持列表和状态占位数据同步扩展。
- 服务停机期间的故事补演或历史回填。
- 新的分布式任务框架、任务管理页面或外部消息队列。

## 13. 完成标准

- 每个整点只对锦鲤、玉兔两个原型进行检查，计算量不随宠物数量增长。
- 每种原型始终最多一条当前状态。
- 多实例部署下，同一原型在同一整点时槽最多完成一次有效计算。
- 概率未命中时保持旧状态且不会因实例数量增加而获得额外抽取机会。
- 成功切换时历史快照与当前状态原子更新。
- 已破壳宠物可通过宠物 ID 查询其原型共享当前状态和历史，未破壳宠物看不到故事数据。
- 相关测试通过，新增代码覆盖率达到项目要求。
