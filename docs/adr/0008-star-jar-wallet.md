# 0008. 星星罐：单表流水 + 强制 refId 幂等 + 流水承载履约状态 + 旅行预订挂原型

- 状态：已接受
- 日期：2026-10-08

## 背景

蛋宝宝需要用户级虚拟货币（星星）：多渠道赚取（签到/广告/邀请/活动/后台补发）存入星星罐，多场景消费（兑换/抽奖/旅行日记预订）。钱包类系统的核心风险是资损：重复入账、负余额、并发超扣。项目已有 `item` 道具模块（SKU 级库存：grant/consume 双流水表 + 唯一索引幂等 + 原子扣减），星星罐看似可直接复用。

旅行场景引入新语义：星星买的不是「旅行」本身——宠物是否旅行由故事引擎按原型（锦鲤/玉兔）自主驱动，故事状态按原型共享（见 CONTEXT.md「故事状态」），无 trip 数据模型、无开始/结束事件。用户花星星预订的是「旅行日记获取权」：该原型线下一次旅行结束时，有预订的用户收到日记。消费发生在旅行开始之前（无 tripId 可引用），履约（日记生成）异步后至。

## 决策

1. **独立 `star` 模块，不复用 item 表**：星星是账户级货币（无量纲、无 SKU、无 totalCount/remainCount 之分），item 是 SKU 级库存，模型不同。只照搬 item 的双流水幂等骨架与原子扣减模式，表结构独立。
2. **单表流水，偏离 item 双表**：earn/consume 同表 `ai_star_transaction`，`type` 区分、`amount` 带正负。钱包语义要求赚/花按时间混排查询，单表天然简单、幂等键空间统一、对账容易。偏离 item 的 grant/consume 双表是有意的。
3. **强制 refId 幂等**：`earn()`/`consume()` 强制调用方传业务单号（签到=日期、兑换=订单号、旅行预订=服务端生成 `tv-` 前缀单号），唯一索引 `(user_id, biz_type, ref_id)` 兜底，`DuplicateKeyException` 转幂等返回。无 refId 直接拒绝——防止内部调用方偷懒造成重复发星。
4. **流水承载履约状态**：加 `fulfill_status`（pending/fulfilled）+ `fulfill_ref_id`（履约产物ID）通用列，而非 travel 专用列。即时场景（兑换/抽奖）写入即 fulfilled；travel 预订写入 pending，故事引擎在旅行结束时调 `consumePendingTravelPreorder` 消耗最早一笔 pending 并回填日记ID。通用列避免未来兑换发货、抽奖开奖等异步履约再加列迁移。
5. **旅行预订挂原型，非 petId**：故事状态按原型共享、用户每原型限一只宠物（领养名额规则），日记归属「锦鲤旅行故事线」而非某个宠物实例。宠物逻辑删除重领养同原型后，预订不丢。流水存 `pet_prototype` 字段（仅 travel 必填）。
6. **不开 HTTP 写接口**：小程序端只读（查余额、分页流水）。所有变动由服务端业务经 Java service 内部直调。客户端可调的发星接口 = 刷星漏洞。
7. **整数星星、永不过期、禁负余额**：扣减走原子条件 UPDATE（`WHERE balance >= ?`，影响行数 0 = 余额不足），与 item 模块 `deductRemain` 同款。

## 否决的替代方案

- **复用 item 模块双流水表**：item 是 SKU 级（grant/consume 按 skuCode 分桶），星星无量纲，强套会引入无意义的 skuCode 占位；且双表无法直接混排查询用户流水。
- **无余额表、sum 流水现算**：随流水增长变慢，且并发扣减无法在 DB 层防透支。
- **travel 专用履约列 `diary_generated`**：兑换/抽奖未来大概率也有异步履约，专用列导致每加一个异步场景就加列。
- **预订挂 petId**：宠物逻辑删除重领养后预订丢失，用户权益受损；故事按原型线驱动，petId 粒度过细且与故事模型错配。
- **预订设有效期（30 天过期退星）**：需定时任务 + 退款逻辑，复杂度高；v1 永久有效，等运营有诉求再加。
- **退款自动化**：旅行中断/宠物删除时 pending 预订不退星，留待人工/后台补；退款属故事引擎异常范畴，不在星星罐边界内。

## 后果

- 星星与道具是两套并行体系：货币（星星）与库存（道具）分离。未来「星星购买道具」由 item 模块调 `star.consume()` 后再 `grant`，跨模块编排，本期不做。
- 旅行功能（开始/结束事件模型、日记生成）尚未实现，`consumePendingTravelPreorder` 暂无真实调用方——接口先行，故事引擎迭代时接入。
- 履约状态通用列对即时场景冗余（永远 fulfilled），但换取了异步履约的统一承载位。
- 赚取/消费枚举写死在代码（Java enum），渠道/场景变更需发版；数量有限，可接受。
