# 0007. NFC 领养成功即静默逻辑删除邀请码宠物（渠道互斥）

- 状态：已接受
- 日期：2026-10-04

## 背景

蛋宝宝有两个宠物创建渠道：邀请码领养（`adopt`）与 NFC 触碰领取（`claim`）。邀请码渠道是产品前期验证小程序玩法的过渡产物，NFC 渠道才是正式主流程。两渠道并存会产生歧义态：同一用户既持有邀请码宠物又持有 NFC 宠物时，主页展示、聊天入口、名额判定都缺规则。

同时 NFC 渠道放开「同一用户可领养多只、同原型限一只」（ADR 0006 后续变更），「已领取过该原型」的重复拦截需要一个不消耗 NFC 资产的语义——被拦截的触碰不能毁掉一张可给他人领取的卡。

## 决策

1. **渠道互斥，双向生效**：NFC 领养成功时，该用户名下未删除的邀请码宠物在同一事务内被逻辑删除（沿用 ADR 0006 的 `deleted_at` 语义）；已有 NFC 宠物的用户使用邀请码领养被拦截，复用 `PET_ALREADY_EXISTS`(10206)。
2. **替换静默执行，无前置确认**：用户在 NFC 领取流程中不弹确认框，领养成功页以轻提示告知原体验宠物已替换。原始数据平台侧保留（逻辑删除不删行），作合规与客服兜底。
3. **重复原型拦截只统计 NFC 来源宠物**：preview/confirm 的 ALREADY_OWNED 判定只查 `source=NFC` 的未删除宠物。仅有邀请码宠物的用户碰同原型 NFC 不拦截，走替换流程。被拦截的触碰不消耗资产——资产保持 ACTIVE，可供他人领取（NFC 资产一次性消耗仅指成功领取，见 GLOSSARY.md「NFC 资产一次性消耗」）。
4. **confirm 单事务**：校验重复原型、逻辑删除邀请码宠物、创建 NFC 宠物、写领取记录在同一数据库事务内，任一步失败整体回滚；幂等由 `(user_id, prototype, deleted_at)` 唯一索引兜底。
5. **多宠物的用户可见形态**：主页上下滑动切换宠物，按领养时间正序，默认停在最先领取的宠物（见 GLOSSARY.md「当前宠物」）。聊天/记忆/画像仍按设备 MAC 锚定，一宠一设备下天然按宠物隔离，不改造。

## 否决的替代方案

- **替换前弹窗确认**：多一步阻断，且邀请码宠物是过渡验证产物，保留它不被视为用户资产承诺。轻提示已足够避免「数据丢失感」投诉。
- **ALREADY_OWNED 按全渠道判定**：会把「只有邀请码玉兔、碰玉兔 NFC」的用户错误拦截，与渠道互斥的替换语义直接冲突。
- **NFC 资产多次复用（不消耗）**：与资产域既有状态机（ACTIVE → CLAIMED + 乐观锁）冲突，且丢失一卡一宠的审计与防伪能力。只有「重复原型拦截」这一未成交场景不消耗资产。
- **聊天/记忆改造挂到 pet_id**：工程量大且收益为零——一宠一设备下 MAC 锚定已等价于按宠物隔离。

## 后果

- 邀请码宠物被替换后用户侧完全消失、无找回入口；数据保留使人工恢复技术上可行。
- 邀请码渠道对已有 NFC 宠物的用户彻底关闭，邀请码功能进入只维护不演进状态。
- 同一物理 NFC 卡的合法触碰结果有三种：成功领取（消耗）、重复原型拦截（不消耗）、已被他人领取（CLAIMED_BY_OTHER）——前端需区分三态文案。
- 主页需新增多宠物滑动切换与「当前宠物」概念；单宠物用户无感知。
