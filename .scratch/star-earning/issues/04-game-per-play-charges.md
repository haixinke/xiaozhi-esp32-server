# 04: 消费型游戏按局扣费

**What to build:** 游戏业务在允许用户开始一局消费型游戏前，可以调用标准内部扣费方法，按当前游戏配置从星星罐扣除费用；余额不足时该局不能开始。同一局重试只扣一次，不同局分别收费，不受每日首次奖励规则限制。

**Blocked by:** 01 游戏奖励与消费配置校验。

**Status:** resolved

## Comments

完成（commit 46989794，merge f130fae0）：新增内部方法 `GameStarChargeService.chargeForPlay(userId, gameType, playSessionId)`，结果区分 NEW_CHARGE/ALREADY_CHARGED/NO_CHARGE；ref_id 用 SHA-256("game-play-charge|gameType|sessionId") 64 位十六进制；防重先于配置校验，重试返回原流水；不存在/停用拒绝（10369），存量冲突配置拒绝（10375）；免费/奖励型游戏扣费入口直接 NO_CHARGE；REQUIRES_NEW 内层事务保证账户+流水+原子扣减同提交，余额不足整体回滚。15 个新测试全绿，全量 1065 run 11 errors 均为基线既有（已用干净 worktree 验证）。附带修复 MessageSourceCacheResetExtension 容忍已移除的 MessageUtils.messageSource 静态字段（否则全测试类 afterAll 报错）。

- [ ] 提供后端内部游戏扣费方法，接收可信用户身份、游戏类型及后端生成或验证的局次业务单号；费用取游戏管理配置，不由客户端指定。
- [ ] 每局开始前完成扣费，成功后调用业务才允许开始；同一天多局分别扣费，不把每日奖励限制套用于消费。
- [ ] 使用独立游戏扣费业务类型，复用现有星星钱包原子扣减与资金流水，不新建游戏结算表或每日奖励表，也不依赖每日奖励能力。
- [ ] 扣费防重复边界为用户、游戏类型和局次单号；同一局重复或并发请求只生成一笔扣款流水，不同用户、游戏或局次不能错误碰撞。
- [ ] 局次业务单号必填且由后端生成或验证，不能用每次网络请求新生成的随机号冒充同一局身份；后续玩法业务负责维护局次身份，本期不实现通用游戏局次状态机。
- [ ] 根据规范序列化的游戏类型与局次单号生成确定性的扣费业务单号，使用64位十六进制SHA-256适配现有流水业务单号长度，避免直接拼接的超长与分隔歧义。
- [ ] 已扣费的同一局重试先返回原流水及原金额，不因配置修改、停用或删除而重新扣款；返回结果明确区分本次新扣费与重复请求。
- [ ] 游戏不存在或停用时拒绝新扣费；存量奖扣同时为正的冲突配置明确拒绝，不静默采用消费金额。
- [ ] 免费双零游戏或奖励型游戏调用扣费入口时直接跳过，不创建星星账户或资金流水；不为零星星请求保存快照。
- [ ] 余额不足时返回项目统一业务错误，不产生成功扣费或负余额；游戏业务不得在扣费失败后允许开始。
- [ ] 并发不同局扣费时余额始终非负；余额更新与流水同事务提交，失败整体回滚，重试不会被失败的残留流水误判为已扣款。
- [ ] 本期不提供退款方法；成功扣费后主动退出、游戏失败或系统异常由人工处理，事务自身失败仍需整体回滚。
- [ ] 先写失败测试再实现；覆盖正常扣费、同局重试、不同局分别扣费、并发同局只扣一次、并发不同局余额不足保护、配置变更重试、免费跳过及失败回滚。
- [ ] 数据库集成测试验证实际余额、流水及并发行为；测试数据独立并清理，运行定向测试及后端全量测试，相关服务有效覆盖率目标80%以上，明确报告既有失败。
- [ ] 仅交付标准内部能力，不接通具体消费游戏，不新增客户端可指定金额的写接口，不修改前端或每日可玩次数语义。
