# 宠物蛋微信小程序与控制板 BLE 通信协议

文档版本：V2.0；协议标识：`PROTO=2`；编制日期：2026-11-23。

实施状态：设备端固件适配及手机联调待执行。现有 V5.0 固件采用 `PROTO=1`，不支持本协议，需完成固件适配后方可使用。本文收发示例用于说明接口约定，不作为实测记录。

本协议规定微信小程序与宠物蛋控制板之间的 BLE 接口、消息格式、控制指令及异常处理要求。设备端指控制板及其 BLE 模块。通信采用请求与应答方式，业务条件由小程序端判定，设备端按指令执行硬件控制。本协议不设置会话号、请求序号、应用层 CRC、心跳及主动事件上报。

## 1 指令总览

文中 `\n` 为换行符的表示形式，发送时应编码为 LF 字节 `0A`。

| 功能 | 请求示例 | 成功应答示例 |
|---|---|---|
| 读取设备信息 | `!INFO\n` | `!OK INFO PROTO=2 FW=DEV LEDS=20 SN=00112233445566778899AABB TYPE=1\n` |
| 查询状态 | `!STATUS\n` | `!OK STATUS HATCH=FRESH MOTOR=0 FAULT=0 LIGHT=OFF\n` |
| 设置灯光 | `!LIGHT BREATHE 255 120 30 40 1600\n` | `!OK LIGHT MODE=BREATHE\n` |
| 关闭灯光 | `!LIGHT OFF\n` | `!OK LIGHT MODE=OFF\n` |
| 启动破壳 | `!HATCH\n` | `!OK HATCH RUNNING\n` |
| 停止电机 | `!STOP\n` | `!OK STOP MOTOR=0 HATCH=ABORTED\n` |

表中 FW、SN 和 TYPE 为示例值。STOP 示例对应破壳运行中的停止操作；HATCH 字段应返回停止后的实际状态。

## 2 职责划分

小程序端负责用户管理、宠物内容、养成进度、破壳条件判定、蓝牙连接及界面交互。业务条件满足后，由小程序端发送 HATCH 指令。

设备端负责灯光控制、电机预设动作执行、定时停机、故障停机及单次破壳动作记录。设备端不保存养成进度，不承担账号及破壳资格校验。设备端通过 SN 标识设备，通过 TYPE 报告宠物类型。

本协议控制范围为 20 颗 RGB 灯珠及破壳电机，不包含磁吸配件、AI 对话及云端业务接口。

## 3 BLE 通信接口

| 项目 | 接口约定 |
|---|---|
| 通信角色 | 手机为 BLE 主机，设备端 BLE 模块为外设 |
| 主服务 | FFF0：`0000FFF0-0000-1000-8000-00805F9B34FB` |
| 指令写入特征 | FFF2：`0000FFF2-0000-1000-8000-00805F9B34FB` |
| 应答通知特征 | FFF1：`0000FFF1-0000-1000-8000-00805F9B34FB`，需订阅通知 |
| 单次写入长度 | 不超过 20 字节，超出部分按顺序分包发送 |
| 写入顺序 | 前一分包写入完成后发送下一分包，建议包间隔 30ms |

上述 UUID 沿用现有项目配置。模块实际 UUID、可写属性及通知属性应在样机联调时确认。小程序端应根据特征属性选择 Write 或 Write Without Response；通知特征仅支持 Indicate 时，应按其属性订阅。设备广播名以样机实际配置为准。

连接建立顺序为：确认样机协议版本 → 扫描并连接 → 发现服务及特征 → 注册接收并订阅 FFF1 → 等待约 200ms → 发送 INFO → 校验 `PROTO=2` → 发送 STATUS → 根据设备状态启用控制功能。

蓝牙写入成功表示写操作完成；指令是否受理由设备端应答确认。INFO 无应答或协议版本不符时，应停止控制并核对固件，不执行旧协议自动探测。

## 4 消息格式与传输规则

请求及应答采用 ASCII 文本，以 `!` 为起始符，以换行为结束符：

```text
!<COMMAND> [ARGS]\n
!OK <COMMAND> <RESULT>\n
!ERR <COMMAND> <CODE>\n
```

尖括号表示字段，方括号表示可选部分，均不作为实际字节发送。命令关键字使用英文大写，参数以单个 ASCII 空格分隔。数值参数使用十进制整数，不附加单位、正负号、小数点或 `0x` 前缀。每条请求仅包含一项操作。

双方统一使用 LF 结束符，同时兼容 CRLF（`0D 0A`）；单独的 CR 不作为消息结束。每行长度不超过 128 字节，包含起始符，不包含结束符。设备端应在完整接收且参数校验通过后处理指令；参数错误时不得变更灯光或启动电机。

发送端应先构造完整消息，再按不超过 20 字节分包，分包之间不插入结束符。接收端应连续缓存通知数据，按换行提取完整消息；单次通知可能包含部分消息或多条消息。

接收到新的 `!` 时，应丢弃尚未完成的消息并重新开始接收。起始符之前的数据忽略，`!` 不得用于消息内容。

设备端自接收 `!` 起，组帧期限为 1 秒。发生组帧超时、长度超限或非法字节时，应丢弃当前消息，返回一次 `!ERR UNKNOWN FRAME\n`，并从下一个 `!` 恢复接收。残缺消息不得执行。小程序端接收处理应同时设置长度限制并丢弃无效消息。

普通请求按串行方式处理，收到对应 OK 或 ERR 后方可发送下一请求。应答中的命令名用于匹配请求；除第 7.2 节规定的 STOP 外，不支持请求并发。状态字段按空格分隔，以 `键=值` 解析；未识别字段保留用于日志记录。

## 5 设备信息与状态查询

### 5.1 设备信息 INFO

```text
!INFO\n
!OK INFO PROTO=2 FW=DEV LEDS=20 SN=00112233445566778899AABB TYPE=1\n
```

PROTO 固定为 2；FW 返回适配后的实际固件版本，长度不超过 16 个字符，允许英文字母、数字、点、下划线及连字符；LEDS 固定为 20。

SN 是设备的唯一标识，不同设备的 SN 不得重复。SN 为 24 位十六进制字符串，应以字符串形式存储和传递，不进行数值转换。

TYPE 是宠物类型，使用十进制整数枚举。

| TYPE | 宠物类型 |
|---|---|
| 1 | 锦鲤 |
| 2 | 玉兔 |

### 5.2 状态查询 STATUS

```text
!STATUS\n
!OK STATUS HATCH=DONE MOTOR=0 FAULT=0 LIGHT=BREATHE\n
```

MOTOR 为电机运行标志，0 表示停止，1 表示运行。FAULT 为当前驱动故障标志，0 表示未检测到故障，1 表示故障有效。LIGHT 返回 OFF 或第 6 节定义的灯光模式名。HATCH 为破壳动作记录状态，定义如下。

| HATCH | 状态定义及处理要求 |
|---|---|
| FRESH | 尚无破壳动作记录，业务条件满足后可请求 HATCH |
| RUNNING | 破壳动作执行中，等待结束或发送 STOP |
| DONE | 定时动作已结束，禁止再次启动 |
| ABORTED | 动作由 STOP 中止，不自动重新执行 |
| INTERRUPTED | 动作期间设备复位或掉电，不自动重新执行 |
| FAULT | 破壳动作发生驱动故障，转维护处理 |
| STORE_ERROR | 动作记录读取或写入异常，转维护处理 |

MOTOR 反映电机实时运行状态，HATCH 反映破壳动作记录，两者应分别处理。FAULT 恢复为 0 不清除已有的 FAULT 动作记录。收到未定义的 HATCH 状态时，应禁止启动并保存原始应答。

## 6 灯光控制

灯光指令统一控制整串 20 颗灯珠，不设置灯珠编号及数量参数。关闭灯光使用 `!LIGHT OFF\n`，其余模式使用以下格式：

```text
!LIGHT <MODE> <R> <G> <B> <BRIGHTNESS> <TIME_MS>\n
```

R、G、B 及 BRIGHTNESS 的取值范围均为 0～255 的整数。BRIGHTNESS 为 0 时输出全暗，该参数不表示电流百分比。SOLID 模式的 TIME_MS 固定为 0，其余模式取值范围为 20～60000ms。

| 模式 | 灯光效果 | TIME_MS 定义 |
|---|---|---|
| SOLID | 指定颜色常亮 | 固定为 0 |
| BLINK | 指定颜色亮灭闪烁 | 完整亮灭周期，亮灭各占半周期 |
| BREATHE | 指定颜色渐亮渐暗 | 完整呼吸周期 |
| ALTERNATE | 相邻灯交替亮灭，背景黑色 | 完整交换周期，每半周期交换一次 |
| CHASE | 单个亮点沿灯串移动，背景黑色 | 单步移动时间 |
| RAINBOW | 设备端生成彩虹，R、G、B 固定为 0 | 单步颜色推进时间 |
| FLOW | 亮点及渐淡拖尾共 3 颗灯，背景黑色 | 单步移动时间 |
| MARQUEE | 亮点间距为 3 个灯位，背景黑色 | 单步移动时间 |

灯光效果持续运行至下一条有效 LIGHT 指令或设备重启。新指令覆盖当前效果，不设置灯效队列，不上报灯效事件。OK 应答表示配置已受理，不作为物理灯光输出的检测结果。

```text
!LIGHT SOLID 255 120 30 32 0\n
!OK LIGHT MODE=SOLID\n

!LIGHT BREATHE 255 120 30 40 1600\n
!OK LIGHT MODE=BREATHE\n

!LIGHT OFF\n
!OK LIGHT MODE=OFF\n
```

以上示例依次为暖橙色常亮、暖橙色呼吸及关闭灯光。设备上电默认关闭灯光，不要求小程序恢复上一次设置。本协议不开放副色、分区、单颗灯、重复次数及宽度参数。

## 7 破壳与停止控制

### 7.1 破壳指令 HATCH

破壳请求为 `!HATCH\n`，不携带电机方向、PWM、角度或运行时长参数。方向、占空比、运行时长及加减速参数由设备端预设，正式参数由硬件及结构方完成标定。

设备端仅在 HATCH 为 FRESH、无驱动故障且电机空闲时受理。受理顺序为：成功保存动作开始记录 → 启动电机 → 返回 `!OK HATCH RUNNING\n`。该应答表示启动请求已受理，不表示破壳完成。

小程序端收到成功应答后，应查询 STATUS，直至 HATCH 不再为 RUNNING，建议查询间隔为 500ms。设备端不主动上报完成事件，不要求心跳维持动作。

```text
!HATCH\n
!OK HATCH RUNNING\n

!STATUS\n
!OK STATUS HATCH=DONE MOTOR=0 FAULT=0 LIGHT=BREATHE\n
```

现有 V5 试验参数为方向 F、PWM 占空比 60%、运行时长 250ms、加减速各 30ms，尚未完成机构标定。V2 适配可沿用该试验参数，单次运行上限保留为 2000ms。运行时长不构成实测角度依据，DONE 仅表示定时动作结束，不表示传感器已确认开壳或到达目标位置。

设备端实行单次破壳动作记录约束。运行中重复请求 HATCH 返回 BUSY；动作完成、中止、故障或掉电中断后再次请求返回 LOCKED。检测到存储异常或当前驱动故障时，分别返回 STORE 或 HARDWARE。重新连接、重新上电及灯光设置均不解除动作记录。

记录写入或驱动启动失败时，设备可能已保存异常动作记录。小程序端收到错误应答后应查询 STATUS，不得据此自动重新启动。本协议不提供动作记录清除指令，维护恢复方式由固件方另行提供。

### 7.2 停止指令 STOP

设备端处理 `!STOP\n` 时，应立即将电机输出置零并关闭驱动，不等待原定运行时长，不改变灯光设置。电机空闲时同样返回 OK。破壳执行中停止时，动作记录置为 ABORTED；记录写入失败时置为 STORE_ERROR。无动作执行时保留原 HATCH 状态。

```text
!STOP\n
!OK STOP MOTOR=0 HATCH=ABORTED\n
```

STOP 允许优先发送。小程序端应取消待发操作；当前消息尚未发送完整时，应取消剩余分包，待当前蓝牙写操作结束后发送完整 STOP 请求。新起始符 `!` 用于清除设备端未完成消息，无需等待原请求应答。

STOP 请求发出后，应等待 `OK STOP` 或 `ERR STOP`。期间收到的其他请求应答不得作为停止确认。STOP 仅关闭电机输出，不执行机械制动、回零或动作记录复位，亦不撤回已发生的运动。

## 8 异常处理

错误应答格式为 `!ERR <COMMAND> <CODE>\n`。COMMAND 为 INFO、STATUS、LIGHT、HATCH 或 STOP；无法识别请求时使用 UNKNOWN。

| 错误码 | 定义 | 小程序端处理要求 |
|---|---|---|
| CMD | 未定义的命令 | 核对命令及协议版本 |
| PARAM | 参数数量、模式、数字格式或取值范围不正确 | 修正参数后重新发送 |
| BUSY | 已有动作执行中 | 查询状态，等待结束或发送 STOP |
| LOCKED | 已有一次破壳动作记录 | 查询并显示结果，禁止再次启动 |
| HARDWARE | 当前驱动故障或电机启动失败 | 查询状态并提交硬件方处理 |
| STORE | 动作记录不可用或写入失败 | 查询状态并转维护处理 |
| FRAME | 消息超长、含非法字节或组帧未完成 | 核对编码及分包，重新建立通信 |

错误应答示例：`!ERR LIGHT PARAM\n`、`!ERR HATCH BUSY\n`、`!ERR HATCH LOCKED\n`、`!ERR UNKNOWN CMD\n`。动作执行期间应支持 INFO、STATUS、STOP 及 LIGHT，灯光设置不得影响电机定时停机及故障处理。

应答超时从最后一个分包写入完成起计，默认时限为 2 秒。发生写入失败、应答超时或应答格式错误时，本次操作结果按未知处理。小程序端应取消待发队列、清空本地未完成消息并断开连接；重新连接后依次执行 INFO 和 STATUS。不得在原连接内自动重试或重新发送待发动作。除 STOP 外，同一时刻仅允许一个请求等待应答。

蓝牙断开后，小程序端应停止状态查询并显示离线。已启动的 HATCH 由设备端独立定时结束，或由 STOP、驱动故障中止；设备实际复位或掉电后，按已保存记录恢复状态。重新连接后应查询 STATUS 确认动作结果，界面动画不得作为判定依据。连接断开时不保证 STOP 能够送达。

## 9 联调验收

本节为固件适配后的待执行验收要求。验收结果应附原始收发记录及相应测量证据。

- 核对固件版本、HEX 及 PROTO=2，验证扫描、连接、通知订阅，以及 INFO、STATUS 应答。
- 核对 INFO 应答中不同设备的 SN 无重复，TYPE 与设备对应的宠物类型一致。
- 验证请求分包、应答分段及单次通知包含多条消息时的解析结果，确认无消息丢失或重复执行。
- 验证灯光颜色、亮度、全部模式及关闭功能；连续切换灯效时，状态查询与电机停止应正常响应。
- 在测试机构上验证 HATCH 受理及结束状态，记录实际方向、顶壳时长、电流及温升。
- 验证重复点击、ACK 丢失及重连场景，已记录的破壳动作不得再次执行。
- 验证动作期间 STOP、断连、驱动故障及掉电场景，异常记录应保留，不得自动恢复 FRESH。
- 验证错误参数、无效消息及超长消息均不触发动作，运行期间 INFO、STATUS、STOP 应可正常使用。

验收记录应包含固件版本、SN、TYPE、手机型号、原始收发文本及时间、动作前后 STATUS，以及相关硬件测量数据。
