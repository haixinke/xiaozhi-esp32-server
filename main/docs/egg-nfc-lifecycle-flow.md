# 蛋宝宝 NFC 全生命周期流程图

> 面向读者：产品、运营、工厂对接、仓储同学、研发新同学。
> 目标：不用先理解代码，也能看懂一件 NFC 蛋宝宝从微信后台配置、生产写卡、仓库激活，到用户触碰领取的完整交互。
> 依据文档：`main/docs/egg-nfc-feature-spec.md`、`docs/superpowers/plans/2026-07-29-egg-nfc-feature.md`。

## 1. 先用一句话理解

NFC 蛋宝宝不是让小程序直接读取芯片内容，而是把“微信可识别的打开小程序链接”写进 NFC 标签里。用户手机触碰标签后，系统拉起微信，微信打开蛋宝宝小程序的领取页，领取页带着一个隐藏的领取标识 `claimRef` 找后端确认这件实物是否可以领取。

每件实物都有三类关键身份：

| 身份 | 谁生成 | 给谁用 | 说明 |
|---|---|---|---|
| `wechat_sn` | 我们服务端 | 微信 `generatenfcscheme` 接口 | 每件实物唯一，告诉微信“这是哪一张 NFC 标签” |
| `claimRef` | 我们服务端 | 小程序领取页和后端 | 用户触碰后带回来的领取凭证，不在管理后台展示完整值 |
| `openlink` / NFC Scheme | 微信返回 | 工厂写入 NFC 标签 | 真正写进 NFC 芯片里的内容 |

一个很重要的边界：`model_id` 是微信审核设备类型后给的设备类型编号，所有蛋宝宝共用一个；`wechat_sn` 和 `claimRef` 是每件实物各自唯一。

## 2. 总览流程

```mermaid
flowchart TD
    A["微信小程序后台配置<br/>申请硬件设备与 NFC 能力"] --> B["取得 model_id<br/>配置到服务端"]
    B --> C["发布小程序领取页<br/>/pages/nfc-claim/nfc-claim"]
    C --> D["管理后台登记发布证据<br/>开启生产前置条件"]
    D --> E["创建 NFC 生产批次<br/>固定 SKU、原型、数量"]
    E --> F["服务端生成每件实物资产<br/>asset_no、wechat_sn、claimRef"]
    F --> G["调用微信 generatenfcscheme<br/>一件商品生成一个 Scheme"]
    G --> H["导出工厂写卡 CSV<br/>SN + Scheme"]
    H --> I["工厂批量写入 NFC<br/>URI Record + AAR"]
    I --> J["工厂回读校验并锁卡<br/>导出写卡结果"]
    J --> K["管理后台导入写卡结果<br/>合格资产进入 VERIFIED"]
    K --> L["仓库确认入库<br/>VERIFIED -> IN_STOCK"]
    L --> M["商品销售/发货时出库扫描激活<br/>IN_STOCK -> ACTIVE"]
    M --> N["用户手机触碰 NFC<br/>微信打开小程序领取页"]
    N --> O["用户登录和绑定手机号"]
    O --> P["预览蛋宝宝原型<br/>不核销"]
    P --> Q["用户点击立即领取<br/>ACTIVE -> CLAIMED"]
    Q --> R["后端创建 EGG 状态 ai_pet<br/>用户进入孵化流程"]
```

可以把整个系统想成四条线协作：

| 线 | 负责什么 | 典型参与者 |
|---|---|---|
| 微信配置线 | 让微信允许 NFC 标签打开小程序 | 小程序管理员、研发 |
| 生产写卡线 | 把每件实物对应的 Scheme 写入 NFC 芯片 | 生产运营、工厂 |
| 库存激活线 | 只让真正出库的商品可被领取 | 仓库、运营后台 |
| 用户领取线 | 用户触碰、登录、预览、确认领取 | 购买用户、小程序、后端 |

## 3. 模块一：微信小程序后台配置流程

这一步解决“微信是否允许你的 NFC 标签打开小程序”的问题。没有这一步，后端不能正式生成可写入标签的 NFC Scheme。

```mermaid
flowchart TD
    A["确认小程序主体条件"] --> B{"是否为国内非个人主体<br/>且已微信认证?"}
    B -->|否| B1["先完成主体认证<br/>否则不能走 NFC 硬件能力"]
    B -->|是| C["确认服务类目<br/>包含 工具-设备管理"]
    C --> D["小程序后台<br/>功能 - 硬件设备"]
    D --> E["开通硬件设备能力"]
    E --> F["添加设备类型<br/>蛋宝宝 NFC 实物"]
    F --> G["提交微信审核"]
    G --> H{"审核通过?"}
    H -->|否| H1["按微信反馈修改资料后重提"]
    H -->|是| I["取得 model_id"]
    I --> J["申请 NFC 标签调起小程序能力"]
    J --> K["选择一机一码模式"]
    K --> L["把正式 model_id 配到服务端<br/>PDC_NFC_MODEL_ID"]
```

关键点：

| 配置项 | 作用 | 第一版策略 |
|---|---|---|
| 设备类型 | 告诉微信“这类 NFC 设备是什么” | 只添加一个“蛋宝宝 NFC 实物” |
| `model_id` | 微信分配的设备类型 ID | 先用配置占位，正式生成前必须填真实值 |
| 一机一码 | 每件实物都有唯一 `sn` | 必须选这个模式 |
| 领取页路径 | 微信打开小程序后进入哪里 | 固定 `/pages/nfc-claim/nfc-claim` |
| 小程序版本 | NFC Scheme 要打开线上发布版 | 生成正式 Scheme 前领取页必须已发布 |

`model_id` 未配置时，管理后台可以显示“待微信审核配置”，但服务端必须禁止生成 Scheme，不能拿占位符去请求微信。

## 4. 模块二：系统初始化和商品类型配置

这一步解决“系统里只有一个固定的 NFC 商品类型”的问题。第一版不做复杂商品类型维护，只初始化一条只读数据。

```mermaid
flowchart TD
    A["执行数据库迁移"] --> B["初始化 pdc_nfc_product_type"]
    B --> C["写入固定商品类型<br/>EGG_BABY_NFC"]
    C --> D["固定领取页路径<br/>/pages/nfc-claim/nfc-claim"]
    D --> E["固定能力模式<br/>ONE_DEVICE_ONE_CODE"]
    E --> F["管理后台只读展示"]
    F --> G{"model_id 是否已配置?"}
    G -->|否| G1["显示待微信审核配置<br/>禁止 Scheme 生成"]
    G -->|是| G2["显示已配置<br/>允许进入后续前置检查"]
```

这里有一个容易混淆的点：

| 字段/配置 | 是什么 | 是否等于 `model_id` |
|---|---|---|
| `pdc_nfc_product_type.capability_mode` | 我们内部记录的能力模式，比如一机一码 | 否 |
| `PDC_NFC_MODEL_ID` | 微信审核通过后给的设备类型编号 | 是真正的 `model_id` |

## 5. 模块三：小程序发布和生产前置检查

正式生成 NFC Scheme 前，必须先保证微信打开的页面已经在线上版本存在。否则标签写好后，用户触碰可能打不开正确页面。

```mermaid
flowchart TD
    A["开发小程序领取页"] --> B["发布小程序正式版"]
    B --> C["确认线上版本包含领取页"]
    C --> D["superAdmin 在管理后台登记发布证据"]
    D --> E["记录版本号、发布时间、验证说明"]
    E --> F{"服务端开关是否就绪?"}
    F -->|否| F1["继续禁止正式生产动作"]
    F -->|是| G["允许创建 Scheme 生成任务"]
```

前置条件可以理解成三把锁：

| 锁 | 为什么需要 | 没打开时会怎样 |
|---|---|---|
| `model_id` | 微信要知道设备类型 | 不能调用 `generatenfcscheme` |
| 发布证据 | 证明领取页已经在线上 | 禁止正式 Scheme 生成 |
| 功能开关 | 控制灰度和紧急暂停 | 关闭生产、激活或领取入口 |

## 6. 模块四：生产批次和 Scheme 生成流程

这一步开始进入“每件商品一条数据”的生产域。

```mermaid
flowchart TD
    A["superAdmin 创建生产批次"] --> B["填写批次号、SKU、原型、数量"]
    B --> C{"数量是否合法?<br/>1 到 10000"}
    C -->|否| C1["拒绝创建"]
    C -->|是| D["服务端一次性创建资产"]
    D --> E["每件资产生成 asset_no"]
    E --> F["每件资产生成 wechat_sn"]
    F --> G["每件资产生成 claimRef"]
    G --> H["claimRef 加密和 HMAC 后入库<br/>不保存明文展示"]
    H --> I["批次状态 DRAFT"]
    I --> J["superAdmin 发起 Scheme 生成任务"]
    J --> K{"前置条件全部满足?"}
    K -->|否| K1["任务不启动<br/>返回具体原因"]
    K -->|是| L["后台异步调用微信 generatenfcscheme"]
    L --> M["微信按 sn + model_id + path + query<br/>返回 openlink"]
    M --> N["服务端加密保存 Scheme"]
    N --> O["资产状态 CREATED -> SCHEME_GENERATED"]
    O --> P["批次进入 READY_FOR_WRITE"]
```

后端调用微信时，每件商品大致传这样的信息：

```text
model_id = 微信给的蛋宝宝设备类型 ID
sn = 这件实物唯一的 wechat_sn
path = /pages/nfc-claim/nfc-claim
query = v=1&ref=<这件实物唯一的 claimRef>
env_version = release
```

`generatenfcscheme` 可以理解为：我们把“设备类型、实物编号、要打开的小程序页面、领取参数”告诉微信，微信返回一个适合写入 NFC 标签的 `openlink`。

如果微信临时超时，任务可以重试；如果是 `model_id` 错误、页面不存在、权限没开通这类配置问题，任务会停止，避免越错越多。

## 7. 模块五：工厂写卡流程

这一步解决“怎么把微信返回的 Scheme 真正写进 NFC 芯片”。

```mermaid
flowchart TD
    A["superAdmin 创建写卡任务"] --> B["选择已经生成 Scheme 的资产"]
    B --> C["服务端生成不可变写卡快照"]
    C --> D["导出写卡 CSV"]
    D --> E["安全交接给工厂"]
    E --> F["工厂导入现有批量写卡设备"]
    F --> G["设备逐张写入 NFC 标签"]
    G --> H["写入 URI Record<br/>Payload 是微信 openlink"]
    H --> I["写入 Android AAR<br/>com.tencent.mm"]
    I --> J["设备逐张回读校验"]
    J --> K{"校验是否通过?"}
    K -->|否| K1["记录失败原因<br/>不进入合格库存"]
    K -->|是| L["设置标签只读"]
    L --> M["导出写卡结果 CSV"]
    M --> N["管理后台导入结果"]
    N --> O["服务端全量校验文件"]
    O --> P{"全部行都合法?"}
    P -->|否| P1["整批导入失败<br/>资产状态不推进"]
    P -->|是| Q["资产进入 WRITTEN 或 VERIFIED"]
```

写卡 CSV 给工厂看的核心列：

| 列 | 说明 |
|---|---|
| `job_no` | 本次写卡任务号 |
| `batch_no` | 生产批次号 |
| `asset_no` | 我们内部的实物资产编号 |
| `wechat_sn` | 给微信的一机一码编号 |
| `uri_payload` | 微信返回的 `openlink`，写入 NFC URI Record |
| `aar_payload` | 固定 `com.tencent.mm`，用于 Android 指向微信 |

NFC 标签里写两条记录：

| NFC Record | 给谁用 | 内容 |
|---|---|---|
| URI Record | iOS 和 Android 都会识别 | 微信返回的 `openlink` |
| Android Application Record | Android 系统辅助定位 App | `com.tencent.mm` |

写卡结果导入时，服务端不会“导入一半成功一半失败”。它会先检查整个文件，确认没有缺行、重复行、串任务、`sn` 不匹配、摘要不一致等问题，全部通过后才统一推进状态。

## 8. 模块六：入库、出库和激活流程

这一步解决“为什么用户买到之前不能提前领取”的问题。写好 NFC 并不代表可领取，只有仓库出库激活后才可以。

```mermaid
flowchart TD
    A["写卡结果导入成功"] --> B["资产状态 VERIFIED"]
    B --> C["仓库确认入库"]
    C --> D{"资产是否全部 VERIFIED?"}
    D -->|否| D1["拒绝入库<br/>提示异常资产"]
    D -->|是| E["资产状态 VERIFIED -> IN_STOCK"]
    E --> F["商品等待销售或发货"]
    F --> G["仓库出库扫描"]
    G --> H["扫码枪输入 asset_no 或 wechat_sn"]
    H --> I["管理后台加入待激活清单"]
    I --> J{"资产是否 IN_STOCK?"}
    J -->|否| J1["拒绝加入清单"]
    J -->|是| K["提交出库激活<br/>携带业务单号和 requestId"]
    K --> L["后端再次全量校验"]
    L --> M{"全部合法?"}
    M -->|否| M1["整批失败<br/>不改变任何资产"]
    M -->|是| N["资产状态 IN_STOCK -> ACTIVE"]
    N --> O["用户触碰后才允许领取"]
```

为什么要“出库激活”：

| 阶段 | 用户触碰 NFC 后的结果 |
|---|---|
| 未写卡或写卡失败 | 通常打不开或不能进入有效领取 |
| 已写卡但未入库 | 后端提示暂时无法领取 |
| 已入库但未出库 | 后端提示暂时无法领取 |
| 已出库并激活 | 可以预览并确认领取 |
| 已领取 | 本人重复触碰返回原宠物，他人触碰提示已领取 |

## 9. 模块七：用户触碰 NFC 和微信端交互

这一步是用户感知最强的流程。

```mermaid
sequenceDiagram
    participant U as 用户手机
    participant NFC as NFC 标签
    participant WX as 微信
    participant MINI as 蛋宝宝小程序
    participant API as 后端

    U->>NFC: 手机靠近蛋宝宝实物
    NFC-->>U: 系统读取 URI Record
    U->>WX: 调起微信并传入 openlink
    WX->>MINI: 打开 /pages/nfc-claim/nfc-claim?v=1&ref=...
    MINI->>MINI: 保存 NFC 领取意图，30 分钟有效
    MINI->>API: 静默登录或恢复登录态
    API-->>MINI: 返回用户登录状态
    MINI->>MINI: 检查是否已绑定手机号
    MINI->>API: preview(claimRef)
    API-->>MINI: 返回商品名、原型、可领取状态
    MINI-->>U: 展示蛋宝宝原型和立即领取按钮
```

这里有几个小白友好的理解点：

| 行为 | 会不会领取成功 | 说明 |
|---|---|---|
| 只是触碰 NFC | 不会 | 只会打开领取页 |
| 打开领取页并看到预览 | 不会 | 预览接口不核销 |
| 用户点“立即领取” | 会尝试领取 | 后端确认资产可领取后才创建蛋宝宝 |
| 用户拒绝手机号授权 | 不会 | 保留意图，用户可稍后重试 |
| 网络断了 | 不会乱扣 | 同一次重试复用 `requestId` |

## 10. 模块八：用户认领事务流程

这一步解决“如何保证一件实物只能被一个用户领取”的问题。

```mermaid
flowchart TD
    A["用户点击立即领取"] --> B["小程序生成 requestId"]
    B --> C["调用 confirm<br/>claimRef + requestId"]
    C --> D["后端校验普通登录态"]
    D --> E{"是否绑定手机号?"}
    E -->|否| E1["返回需要绑定手机号<br/>不核销"]
    E -->|是| F["校验 claimRef 格式"]
    F --> G["用 HMAC 查找资产<br/>不按明文查询"]
    G --> H{"资产是否存在?"}
    H -->|否| H1["返回不可用"]
    H -->|是| I["数据库锁定资产行<br/>SELECT FOR UPDATE"]
    I --> J{"是否同 requestId 重试?"}
    J -->|是| J1["请求一致则重放原结果<br/>请求不同则幂等冲突"]
    J -->|否| K{"资产是否已 CLAIMED?"}
    K -->|本人已领取| K1["返回原 PetVO"]
    K -->|他人已领取| K2["提示已被领取"]
    K -->|未领取| L{"资产是否 ACTIVE?"}
    L -->|否| L1["返回暂时无法领取"]
    L -->|是| M["按资产固定原型创建 ai_pet"]
    M --> N["写入领取记录"]
    N --> O["资产 ACTIVE -> CLAIMED"]
    O --> P["事务提交"]
    P --> Q["小程序保存宠物并进入首页孵化"]
```

关键保障：

| 保障 | 作用 |
|---|---|
| `SELECT ... FOR UPDATE` | 两台手机同时抢同一件时，数据库只让一个事务先成功 |
| `asset_id` 唯一领取记录 | 一件实物最多成功领取一次 |
| `(user_id, request_id)` 幂等 | 网络重试不会重复创建宠物 |
| 本人重复触碰返回原宠物 | 用户不会因为多次触碰而多领 |
| 他人触碰已领商品提示已领取 | 不泄露领取人信息 |

领取成功时只创建 `EGG` 状态的 `ai_pet`，不会提前创建 `ai_device`、`ai_agent`。后续孵化、破壳仍走现有蛋宝宝流程。

## 11. 模块九：状态机总图

下面这张图是实物资产的一生。

```mermaid
stateDiagram-v2
    [*] --> CREATED: 创建批次时生成资产
    CREATED --> SCHEME_GENERATED: 微信 Scheme 生成成功
    SCHEME_GENERATED --> WRITTEN: 工厂写入成功但未完全验证
    WRITTEN --> VERIFIED: 回读一致且锁为只读
    SCHEME_GENERATED --> VERIFIED: 写入、回读、锁卡一次性全部成功
    VERIFIED --> IN_STOCK: 仓库确认入库
    IN_STOCK --> ACTIVE: 出库扫描激活
    ACTIVE --> CLAIMED: 用户确认领取

    CREATED --> SCRAPPED: 生产前报废
    SCHEME_GENERATED --> SCRAPPED: Scheme 后报废
    WRITTEN --> SCRAPPED: 写坏且无法返工
    VERIFIED --> SCRAPPED: 入库前质检报废

    IN_STOCK --> DISABLED: 库存禁用
    ACTIVE --> DISABLED: 未领取售后或风控禁用
    CLAIMED --> DISABLED: 已领取售后作废旧实物
```

状态含义：

| 状态 | 小白解释 | 用户能否领取 |
|---|---|---|
| `CREATED` | 系统里有这件商品，但还没拿到微信 Scheme | 否 |
| `SCHEME_GENERATED` | 微信打开链接已生成，准备交给工厂写卡 | 否 |
| `WRITTEN` | 芯片写过了，但还没有完全验收合格 | 否 |
| `VERIFIED` | 写卡、回读、锁卡都合格 | 否 |
| `IN_STOCK` | 已入库，等待销售或发货 | 否 |
| `ACTIVE` | 已出库激活，买家可以领取 | 是 |
| `CLAIMED` | 已被领取并创建蛋宝宝 | 本人可重复查看，他人不可领取 |
| `SCRAPPED` | 生产阶段报废，不可恢复 | 否 |
| `DISABLED` | 售后或风控禁用，保留历史 | 否 |

## 12. 模块十：权限和数据安全流程

生产库存是后台核心能力，只有 `superAdmin` 可以操作。小程序用户领取接口不要求 `superAdmin`，只要求普通用户登录并绑定手机号。

```mermaid
flowchart TD
    A["请求进入 NFC 功能"] --> B{"请求来源"}
    B -->|管理后台 /pdc/nfc/admin/**| C["校验 superAdmin"]
    C -->|不是| C1["拒绝访问<br/>不返回生产数据"]
    C -->|是| C2["允许商品类型、批次、写卡、库存、激活、审计操作"]
    B -->|小程序 /pdc/nfc/claim/**| D["校验普通登录态"]
    D -->|未登录| D1["引导登录"]
    D -->|已登录| E["确认领取时校验手机号"]
    E -->|未绑定| E1["引导手机号授权<br/>不核销"]
    E -->|已绑定| E2["允许 preview 或 confirm"]
```

敏感数据处理原则：

| 数据 | 是否展示 | 说明 |
|---|---|---|
| `claimRef` 完整值 | 不展示 | 只在小程序 query 中使用，后端加密和 HMAC 保存 |
| 完整 Scheme / `openlink` | 默认不展示 | 只在 superAdmin 下载写卡 CSV 时出现 |
| AppSecret / access token | 永不展示 | 只能在可信服务端使用 |
| `model_id` | 可以展示 | 它不是密钥，只是微信设备类型编号 |
| `tag_uid` | 后台详情谨慎展示或脱敏 | 小程序端不展示 |
| 领取人信息 | 小程序不展示给他人 | 避免泄露隐私 |

## 13. 模块十一：异常和售后流程

```mermaid
flowchart TD
    A["发生异常"] --> B{"异常类型"}
    B -->|model_id 未配置| B1["禁止 Scheme 生成<br/>提示待微信审核配置"]
    B -->|领取页未发布| B2["禁止正式 Scheme 生成<br/>先发布小程序"]
    B -->|微信临时失败| B3["后台任务重试<br/>资产保持原状态"]
    B -->|微信权限或参数错误| B4["停止任务<br/>提示配置问题"]
    B -->|写卡失败| B5["保留失败记录<br/>可重建写卡任务"]
    B -->|回读不一致| B6["不得入库<br/>返工或报废"]
    B -->|标签锁错| B7["标记 SCRAPPED<br/>补发新资产"]
    B -->|未激活被触碰| B8["提示暂时无法领取<br/>记录预激活访问"]
    B -->|两人同时领取| B9["一个成功<br/>另一个提示已领取"]
    B -->|已领取后售后| B10["旧实物 DISABLED<br/>不解绑宠物"]
```

售后原则：

| 场景 | 处理 |
|---|---|
| 未领取的实物有问题 | 禁用或报废旧资产，补发新实物 |
| 已领取的实物有问题 | 作废旧实物，但保留用户宠物和领取记录 |
| 用户想换绑或转赠 | 第一版不支持 |
| 标签被复制 | 首位成功领取者获得商品，这是第一版接受的业务风险 |

## 16. 最终交互闭环

一件 NFC 蛋宝宝完整闭环如下：

```mermaid
flowchart LR
    A["微信允许"] --> B["系统建档"]
    B --> C["微信生成 Scheme"]
    C --> D["工厂写卡"]
    D --> E["回读锁卡"]
    E --> F["仓库入库"]
    F --> G["出库激活"]
    G --> H["用户触碰"]
    H --> I["小程序预览"]
    I --> J["用户确认"]
    J --> K["创建蛋宝宝"]
    K --> L["进入孵化"]
```

只要记住一个判断标准：用户真正能领取的唯一状态是 `ACTIVE`。在此之前，所有流程都是为了安全、可追溯地把一件实体商品准备好；在此之后，领取事务负责把这件实体商品和用户账号、蛋宝宝宠物准确绑定起来。
