# 0006. 宠物实例逻辑删除：deleted_at 时间戳标记 + 手动过滤 + 唯一索引改造

- 状态：已接受
- 日期：2026-10-01

> 后续变更（2026-10-04）：「一人一宠」已调整为分渠道领养名额规则——NFC 渠道同一原型限一只、可领养多只；邀请码渠道仍限一只。唯一索引与领养预检查的约束口径将随代码改造调整，最新规则见 GLOSSARY.md「领养名额规则」。本 ADR 的删除语义（逻辑删除、手动过滤、不级联打标）不受影响。

## 背景

蛋宝宝需要"删除宠物"能力：用户删除后数据保留在库中（审计与潜在人工恢复），小程序侧完全隐藏。两个既有约束使"照抄先例"不可行：

1. `ai_pet` 存在唯一索引 `uk_ai_pet_user_id(user_id)`（一人一宠的 DB 层硬约束）。逻辑删除保留旧行后，若索引不改，用户删除宠物再领养会直接撞唯一键。
2. 仓库唯一的逻辑删除先例是 `ai_agent_tag` 的 `deleted TINYINT` + 手动过滤（`AgentTagServiceImpl`），全仓库未使用 MyBatis-Plus `@TableLogic`。但 `deleted TINYINT` + `(user_id, deleted)` 复合唯一索引只允许每个用户存在一条已删除宠物，删第二只即撞键，不满足"删除释放领养名额、可反复领养删除"的规则。

## 决策

1. **删除标记用 `deleted_at BIGINT NOT NULL DEFAULT 0`**：0 表示未删除，删除时写入 epoch 毫秒。单字段兼任删除标记与删除时间，且同一用户多次删除天然取不同值，配合改造后的唯一索引 `(user_id, deleted_at)` 不撞键。不用 NULL 表示未删除——MySQL 唯一索引允许多个 NULL，活跃宠物的一人一宠约束会失效。
2. **手动过滤，不引入 `@TableLogic`**：所有宠物读取点显式加 `deleted_at = 0` 条件（沿用 AgentTag 模式）。`@TableLogic` 会自动过滤包括智控台在内的全部查询，与"智控台管理员视图暂不过滤、仍见全量"冲突。
3. **统一语义"已删除 = 不存在"**：列表、领养名额检查、实时上下文（pet-context）、故事/生图/集卡/孵化的 petId 归属校验全部过滤，无豁免。删除接口对已删除或不存在的宠物返回"宠物不存在"业务错误，不做幂等成功。
4. **关联数据不级联打标**：聊天记录、故事状态、生图任务、NFC 绑定等关联表不加删除字段，靠入口随宠物消失而隐藏。破壳时创建的 `ai_device`（1:1）保留不动，聊天历史经 `mac_address` 的链路不断。

## 否决的替代方案

- **`@TableLogic` 全局自动过滤**：会波及智控台管理员全量视图，且是仓库首个 `@TableLogic` 用法，与既有手动先例不一致。手动过滤的固有代价是未来新增宠物读取点可能忘记加过滤，由代码评审与"已删除=不存在"统一语义兜底。
- **`deleted TINYINT` + `(user_id, deleted)` 复合索引**（AgentTag 先例的直搬）：每用户只允许一条已删除宠物，第二次删除撞唯一键。AgentTag 无唯一约束场景，先例在此不适用。
- **直接删除 `uk_ai_pet_user_id`，只靠 service 检查**：丢掉 DB 层兜底，并发领养/删除竞态下一人一宠约束失守。不接受。
- **级联给关联表加删除字段**：改动面爆炸且当前无任何按关联表直接展示已删宠物数据的入口，YAGNI。
- **删宠时一并删除 `ai_device`**：聊天历史经 `mac_address` 挂在设备上，删设备使历史断链；设备孤儿态（pet-context 返回空、agent 配置仍在）是可接受的边缘态。

## 后果

- 删除释放领养名额：用户删除后可立即领养新宠，新旧宠物数据完全隔离；旧宠 NFC 卡触碰行为不变（本轮不解绑）。
- `deleted_at` 取 epoch 毫秒，同一用户同一毫秒内连续两次删除理论上撞唯一键——实际领养流程耗时使该窗口不可达，不做额外处理。
- 用户视角删除不可逆、无找回入口；数据保留使客服/DBA 人工恢复技术上可行。
- 新增宠物读取点时必须记得加 `deleted_at = 0` 过滤——手动模式的固有遗漏风险，靠统一语义与评审控制。
