# 03: 奖励型游戏每天首次完成发奖

**What to build:** 游戏业务确认用户成功完成奖励型游戏后，可以调用标准内部方法，将游戏管理中配置的固定星星存入用户星星罐。每用户、每种游戏、北京时间每天仅首次成功完成可获奖，后续游玩直接返回当天已领取，不新增资金或奖励记录。

**Blocked by:** 01 游戏奖励与消费配置校验；02 小纸条连续奖励与统一每日奖励能力。

**Status:** resolved

## Comments

完成（commit 8fa51316，merge 3128c979）：新增 `GameStarRewardService.claimGameReward(userId, gameType)`，结果区分 NEW_REWARD/ALREADY_REWARDED/NO_REWARD；StarDailyRewardServiceImpl 拆出 `claimWithDecision(...)` 决策变体——GAME 走固定金额（不再套连续公式），DAILY_NOTE 保持 11/+1/17；免费/消费型游戏奖励入口 skip 不写任何数据；防重先于配置校验，停用/改配置/删除后重试返回原记录；冲突配置拒绝（10375）；并发 6 线程仅 1 次入账。15+5 新测试全绿，定向 98 全绿，全量 1112 run 9 errors 均基线既有。

- [ ] 提供后端内部游戏奖励方法，按游戏类型读取游戏管理配置，复用统一每日奖励能力和现有钱包，不复制每日资格及入账逻辑。
- [ ] 固定奖励取当前有效配置的赚取星星数，不随连续参与天数增加，也不接受客户端指定金额。
- [ ] 奖励资格按用户、游戏类型和 Asia/Shanghai 日期计算；不同游戏当天可各获一份，不同用户互不影响，切换宠物或设备不增加机会。
- [ ] 仅在游戏业务验证成功完成后调用；中途退出或失败不占奖励机会。本期不接入具体游戏完成事件，不新增通用游戏完成 HTTP 接口或完成事件单号字段。
- [ ] 完成事实、时效及旧事件重试由未来接入业务结合实际完成记录验证，不宣称每日唯一键单独解决跨日重放问题。
- [ ] 小纸条奖励与游戏奖励使用不同来源，互不占用当天资格；打开小纸条后完成推荐游戏仍可获一份对应游戏奖励。
- [ ] 当天已领取时返回明确的已领取结果；可返回原奖励金额及流水标识，但必须标明本次新增数量为零，不新增奖励记录或流水。
- [ ] 奖励已成功发放后，同用户同游戏当天重试先返回原记录，不因游戏奖励变更、停用或删除而重新计算、重复发奖或丢失原结果。
- [ ] 尚未发奖的游戏不存在或停用时拒绝新发奖；存量奖扣同时为正的冲突配置明确拒绝，不静默选取其中一种金额。
- [ ] 免费双零游戏、消费型游戏的奖励入口直接跳过，不创建星星账户、奖励记录或资金流水，不占当天奖励机会；免费游戏后续改为奖励型后，新符合条件的成功完成仍可领取。
- [ ] 并发成功完成或不同请求号不能绕过当天一次限制；奖励记录、余额及流水同事务提交，失败整体回滚并允许重试。
- [ ] 先写失败测试再实现；覆盖每游戏每日一次、用户隔离、跨宠物设备、次日资格、无连续累加、小纸条独立、配置变更重试、免费跳过、无效配置及并发回滚行为。
- [ ] 复用已交付的账户锁及当前读约定；数据库集成测试验证余额、每日奖励与流水实际一致，测试数据独立并清理。
- [ ] 运行定向测试和后端全量测试，相关服务有效覆盖率目标80%以上，记录实际结果及既有失败。
- [ ] 不新增独立游戏结算表，不记录当天重复游玩未获奖的数据，不实现退款、不修改每日可玩次数语义或前端。
