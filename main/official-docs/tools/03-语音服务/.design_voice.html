二、系统概述

2.1 软件用途

本系统为 ESP32 智能硬件提供实时语音 AI 助手服务端能力。设备通过 WebSocket 建立长连接后，持续上传 Opus 编码音频流；系统完成语音活动检测、语音识别、意图理解、大模型推理与语音合成，将合成音频流式回传设备播放，实现自然流畅的端到端语音对话。同时系统通过 HTTP 端点提供 OTA 固件升级与视觉分析能力。系统是 AI 语音陪伴硬件产品的后端中枢，承载对话、记忆、工具调用与设备管理四大核心业务。

三、系统架构设计

3.1 总体架构

本系统采用双服务异步架构，由一个入口模块 app.py 同时启动 WebSocket 服务与 HTTP 服务，两者共享同一份配置与 Provider 实例池。WebSocket 服务面向设备实时音频交互，HTTP 服务面向管理与升级类无状态请求。双服务运行于同一 asyncio 事件循环，通过共享的 ConnectionHandler 与 Provider 工厂协同工作。该设计避免了跨进程通信开销，同时以协程隔离保证了各连接与各请求的独立性。

图 1 系统总体架构图（四层分层 + 外部依赖）

3.2 分层设计

系统自上而下分为接入层、编排层、能力层、存储层四层，层间通过抽象接口解耦，逐层职责单一。接入层只管协议与鉴权，编排层只管状态与流转，能力层只管具体 AI 算法的执行，存储层只管持久化与召回。层间依赖单向向下，上层不感知下层具体实现，通过工厂与基类间接调用。

层次模块职责
接入层websocket_server / http_server / auth协议接入、JWT 鉴权、连接生命周期
编排层connection / handle连接状态机、消息分发、流水线编排
能力层core/providers/* （asr/tts/llm/vad/intent/memory/tools）六大能力 Provider 实现与工具调度
存储层OceanBase / Redis / 智控台 API向量记忆、图谱、缓存、远程配置

3.3 Provider 模式

系统的核心设计是 Provider 模式。每种 AI 能力定义一个抽象基类（如 ASRProviderBase），声明统一接口；具体实现（如 AliyunASR、FunLocalASR、TencentASR 等）继承基类；由 core/utils/ 下的工厂函数（如 asr.create_instance(class_name)）根据配置键动态实例化。该设计使得服务商切换仅需修改配置而无需改动业务代码，符合开闭原则与依赖倒置原则。

4.2 认证与设备绑定

WebSocket 握手阶段由 WebSocketServer._handle_auth 完成。设备在握手时携带 JWT 或 Oauth-Token，服务端校验 auth_key 签名或调用智控台 API 验证设备合法性。认证通过后分配 client_id 并创建 ConnectionHandler。未绑定设备进入待绑定提示流程，由 _discard_message_with_bind_prompt 引导用户完成绑定。auth_key 同时用于 OTA Token 生成与视觉接口 JWT 签发，是系统根密钥。

auth_key 优先级：配置 server.auth_key > 智控台 manager-api.secret > 随机 uuid4.hex。随机密钥仅用于无智控台的本地开发，生产环境必须显式配置以保证多实例一致。

4.3 音频 I/O 与 Opus 编解码

设备上传的音频为 Opus 编码包，服务端在 _decode_opus_packet 中调用 ffmpeg 解码为 PCM 帧。回传音频同样经 Opus 编码后发送。Opus 编解码隔离在 core/utils/opus_encoder_utils.py，保证业务层只处理 PCM。编码参数（采样率 16kHz、声道数、比特率）可配置，适配不同网络条件。编解码通过子进程调用 ffmpeg，避免阻塞事件循环。

4.4 AEC 回声消除

设备扬声器播放的合成语音会被麦克风重新采集，若不消除将导致 ASR 把系统输出识别为用户输入，形成"自言自语"。系统在 _apply_aec 中缓存近期播放的 PCM 帧，与当前收音帧做对齐相减，剔除回声成分。_check_aec_cache_expiry 定时清理过期缓存，防止内存膨胀。该机制使设备在播放语音的同时仍可被唤醒打断，实现全双工对话。AEC 缓存按时间戳对齐，保证消除精度。

4.5 MQTT 音频桥接

除 WebSocket 外，系统支持通过 MQTT 通道接收音频消息，由 _process_mqtt_audio_message 处理。该路径用于非 WebSocket 组网场景（如经 mqtt-gateway 转发的局域网设备），消息统一汇入 _put_asr_audio_with_aec 与 _put_asr_audio 进入 ASR 流水线，保持下游处理一致。该设计使系统能同时服务直连与网关转发两类设备。

4.6 超时与无语音关闭

系统对空闲连接设超时保护：close_connection_no_voice_time（默认 120 秒）无语音输入即关闭连接，释放资源。_check_timeout 协程定时检测，超时触发 _save_and_close。tts_timeout（默认 10 秒）保护 TTS 合成不至无限等待，tool_call_timeout（默认 30 秥）保护工具调用不至阻塞对话。三类超时共同保障系统在异常客户端下的稳定性。

4.7 重启与重连

handle_restart 处理设备主动重启请求，清理当前连接状态后重新初始化。_init_connection_state 重置连接级状态，_save_and_close 保存对话摘要后关闭。设备重连时按 client_id 复用已初始化的 Provider 实例，避免重复加载模型的昂贵开销。

五、语音交互流水线设计

5.1 流水线总览

语音交互是本系统的核心数据流，由 core/handle/ 下的处理器协同完成。一帧音频从设备到达，到合成语音回传，依次经过 VAD、ASR、意图、LLM、TTS 五个阶段，每个阶段均为流式处理，首字延迟可控制在秒级。流水线各阶段通过 asyncio 队列衔接，前一阶段产出即可被后一阶段消费，形成流水线并发，而非串行等待。

图 3 语音交互时序图（VAD→ASR→意图→LLM→TTS 全链路）

5.2 VAD 语音活动检测

VAD（core/providers/vad）判断 PCM 帧是否含人声。当连续帧判定为语音时触发 ASR 开始识别；判定静音时触发 ASR 结束并产出文本。receiveAudioHandle 调用 conn.vad.is_vad(conn, pcm_frame) 完成逐帧判断。当 VAD 暂停（如设备播放中）时，resume_vad_detection 协程在播放结束后恢复检测。VAD 默认基于 silero_vad 模型，亦支持基于能量的 SimpleVAD 实现。VAD 的灵敏度与静音判定阈值可配置。

5.3 ASR 语音识别

ASR Provider 接收 PCM 帧流式识别，支持本地 FunASR/SenseVoice/sherpa_onnx 与云端阿里云/腾讯云/百度/讯飞/豆包/OpenAI/Vosk 等多种实现。conn.asr.receive_audio(conn, pcm_frame, have_voice) 持续喂入音频，识别结果通过回调汇入意图处理。VAD 与 ASR 解耦：VAD 只管切分语音段，ASR 只管把段转写为文本。流式 ASR 在用户说话过程中即开始产出部分结果，配合 VAD 静音判定确认最终文本。

ASR Provider 实现清单（core/providers/asr/）：aliyun_stream、aliyun、aliyunbl_stream、baidu、doubao_stream、doubao、fun_local、fun_server、openai、qwen3_asr_flash、sherpa_onnx_local、tencent、vosk、xunfei_stream，共 14 种实现，覆盖本地推理与主流云服务商。

5.4 意图识别

intentHandler.handle_user_intent 在 ASR 产出文本后先行判断：若命中预设意图（如控制设备、查询天气、退出对话），直接执行对应工具并产出响应，跳过 LLM 以降低延迟与成本；若未命中，文本进入 LLM 对话。意图识别由 core/providers/intent 的 Provider 实现，支持基于关键词的 KeywordIntent 与基于大模型的 LLMIntent 两种策略。意图命中后可调用 speak_trusted_text 直接产出可信文本，不经 LLM 生成，保证特定指令的即时响应。

5.5 LLM 大模型推理

LLM Provider（core/providers/llm）接收对话历史与系统提示词，流式产出回复文本。系统在 ConnectionHandler.chat 中编排完整对话：构造 messages → 调用 LLM → 流式接收 → 实时送入 TTS → 处理工具调用。_handle_function_result 负责把工具执行结果回灌 LLM 继续生成。LLM 支持 OpenAI 兼容接口、本地 vLLM、通义千问、DeepSeek、智谱、Dify、FastGPT、Gemini、Ollama、Xinference、Coze、HomeAssistant 等共 11 类实现。system_prompt.py 模块支持运行时动态系统提示词管理。

5.6 TTS 语音合成与句子切分

TTS Provider（core/providers/tts）将 LLM 流式产出的文本按标点切分为句子，边生成边合成，产出的 Opus 包按 FIRST / MIDDLE / LAST 三态标记入队 tts_audio_queue。该设计使设备能在首句合成完成即开始播放，无需等待整段文本合成完毕。sendAudioHandle 按句子序号有序消费队列回传，保证播放顺序正确。TTS 实现清单（core/providers/tts/）共 20 种：alibl_stream、aliyun_stream、aliyun、cozecn、custom、default、doubao、edge、fishspeech、gpt_sovits_v2、gpt_sovits_v3、huoshan_double_stream、index_stream、minimax_httpstream、openai、paddle_speech、siliconflow、tencent、xunfei_stream，支持流式合成与音色克隆。

5.7 流式与并发控制

流水线各阶段通过 asyncio 协程与队列衔接，ASR、LLM、TTS 并发执行而非串行等待。audioRateController（core/utils/audioRateController.py）控制回传音频的速率，避免设备缓冲溢出；output_counter 统一管理输出序号，支持内容安全门控按序阻断或释放。当 LLM 流式产出与 TTS 合成速度不匹配时，速率控制器动态调节发送间隔，保证平滑播放。

5.8 中断与 abort

用户可在对话进行中打断（abort）。abortHandle 接收打断指令后，清理 TTS 队列（clearSpeakStatus）、重置音频状态（reset_audio_states）、停止当前 LLM 生成。AEC 机制保证打断时设备收音不受自身播放影响。中断后流水线立即就绪，接受下一轮对话，实现自然插话体验。

七、Provider 工厂设计

7.1 工厂模式实现

所有 Provider 通过工厂函数实例化。工厂函数接收配置中的类名，动态导入对应模块并构造实例。以 ASR 为例：

# core/utils/asr.py
def create_instance(class_name: str, *args, **kwargs) -> ASRProviderBase:
    module = importlib.import_module(
        f"core.providers.asr.{class_name.lower()}"
    )
    cls = getattr(module, class_name)
    return cls(*args, **kwargs)

该模式使新增服务商只需在 core/providers/<能力>/ 下新增实现类并配置类名，无需改动工厂与业务代码，符合开闭原则。工厂函数统一返回抽象基类类型，业务层面向接口编程而非具体实现。

7.2 懒加载与后台初始化

Provider 不在启动时全部构造，而在连接首次需要时由 _initialize_components 按需创建。重型 Provider（如本地 ASR 模型加载）通过 _background_initialize 在后台协程中初始化，避免阻塞首个音频帧的处理。已初始化的实例按 client_id 缓存，同设备重连可复用。modules_initialize.py 是统一初始化入口，按依赖顺序初始化各 Provider。

9.1 HTTP 服务

SimpleHttpServer（core/http_server.py）基于 aiohttp 构建，监听默认端口 8003，提供 OTA 与视觉分析两类端点。路由在启动时通过 app.add_routes 注册，base_handler.py 提供通用请求处理基类。服务与 WebSocket 共享事件循环与配置。

9.2 OTA 固件升级

OtaHandler（core/api/ota_handler.py）提供 /xiaozhi/ota/ 端点。设备请求时携带当前版本与设备型号，服务端返回最新固件元数据（版本号、大小、MD5、下载地址）；设备按元数据请求 .bin 文件完成下载升级。OTA Token 通过 auth_key 签名生成，保证升级请求合法。固件包带 MD5 校验，设备下载后验证完整性。

9.4 鉴权设计

HTTP 接口采用 JWT 鉴权。系统启动时确定 auth_key，优先级为：配置文件 server.auth_key > 智控台 manager-api.secret > 随机生成 uuid4.hex。auth_key 同时用于 WebSocket 握手鉴权、OTA Token 生成与视觉接口 JWT 签发，是系统的根密钥。鉴权逻辑隔离在 core/auth.py 与 core/utils/auth.py。生产环境必须显式配置 auth_key，避免随机密钥导致多实例不一致。

十、记忆与知识图谱设计

10.1 记忆模块

Memory Provider（core/providers/memory）基于 PowerMem SDK 实现长期记忆。每轮对话结束后，_log_dialogue_summary 生成对话摘要，提取值得记忆的事实（用户偏好、事实、事件），向量化后存入 OceanBase 向量库。下一轮对话前，_initialize_memory 根据当前输入召回相关记忆，注入 LLM 上下文，实现跨会话的个性化。记忆是语音陪伴产品"记得用户"体验的技术基础。

10.2 用户画像

UserMemory 自动从对话中提取用户画像特征（性格、兴趣、关系网络等），结构化存入知识图谱。画像随对话持续更新，使系统能够根据用户特征调整对话风格与内容推荐。画像提取基于 PowerMem 的 user_profile_prompts 提示词模板，由 LLM 完成结构化抽取。

10.3 知识图谱存储

知识图谱基于 OceanBase 图存储（pyobvector）。节点为实体（人、物、概念），边为关系。图谱与向量库协同：向量库负责语义相似召回，图谱负责关系推理。两者共同构成设备的长期记忆中枢。oceanbase_graph.py 管理图谱的读写，oceanbase_vector.py 管理向量的读写。

10.4 记忆与对话集成

记忆召回发生在 chat 方法入口：输入文本 → 记忆 Provider 召回相关片段 → 拼入 system prompt 或 messages → 送入 LLM。prompt_manager 与 _init_prompt_enhancement 将召回的记忆与用户画像增强进系统提示词，使 LLM 在生成时具备用户历史上下文。该机制使设备"记住"用户跨次对话的关键信息。

10.5 记忆 Provider 选型

生产环境默认 powermem（PowerMem + OceanBase），开发环境可用 mem_local_short（本地短期）或 nomem（无记忆）。mem_report_only 仅持久化摘要不做召回，用于节省成本场景。volmem0 与 mem0ai 提供替代 SDK 实现。选型通过 selected_module.Memory 配置切换。

10.6 上下文源配置

系统支持 context_providers（上下文源）配置，允许在对话前注入外部上下文（如设备状态、环境信息）。上下文源与记忆召回协同，共同构成 LLM 的完整上下文，使对话具备场景感知能力。

十一、配置系统设计

11.1 三层配置机制

系统配置采用三层递进覆盖机制（后层覆盖前层同名键）：

  1. 基础配置：config.yaml，已提交仓库，含默认值与注释说明，是配置的基线。不应直接修改，便于随版本升级。
  2. 本地覆盖：data/.config.yaml，不受版本控制，存放密钥与本地差异化配置。应用启动时必须存在，可空文件。已加入 .gitignore。
  3. 远程覆盖：若 data/.config.yaml 中配置了 manager-api.url，启动时从智控台拉取远程配置覆盖本地。该层优先级最高。

重要：若使用了智控台，则本地所有 AI 相关配置均不生效，全部以智控台下发为准，实现集中运维。

11.2 配置加载器

config/config_loader.py 实现配置的递归合并：读 config.yaml → 合并 data/.config.yaml → （可选）请求智控台 API 合并远程配置。合并采用深递归，对 dict 递归合并而非整体替换，保证局部覆盖不丢失其他默认项。结果缓存供全局读取，避免重复 IO。settings.py 的 load_config 是统一入口。

11.3 远程配置与热更新

智控台 manager-api 通过 REST 接口向本系统暴露运行时配置，使管理员在智控台调整 AI 参数（如切换 LLM 服务商、修改系统提示词、调整 TTS 音色）后，本系统下次拉取即生效，无需重启。update_config 方法支持运行时重新拉取配置。该设计是"智控台—语音服务"联动的关键，实现运维零停机。

十二、关键技术设计

12.1 流式处理与首字延迟优化

本系统对实时性要求极高。全链路采用流式处理：VAD 逐帧判断、ASR 流式识别、LLM 流式生成、TTS 流式合成与句子切分。各阶段通过 asyncio 队列衔接，前一阶段产出即可被后一阶段消费，形成流水线并发。该设计使首字延迟（用户说完到设备开始播放回复）可控制在秒级，是语音交互体验的核心指标。performance_tester 提供基准测试量化该指标。

12.2 Opus 编解码

ESP32 设备与服务端之间的音频传输采用 Opus 编码，低带宽高音质。服务端在 opus_encoder_utils 中封装 ffmpeg 编解码，业务层只处理 PCM。编码参数（采样率 16kHz、声道、比特率）可配置，适配不同网络条件。编解码通过子进程调用 ffmpeg，避免阻塞事件循环。

12.3 AEC 声学回声消除

全双工对话要求设备播放语音时仍可被用户打断。系统在 _apply_aec 中缓存近期播放的 PCM，与收音帧对齐相减消除回声。_check_aec_cache_expiry 定时清理过期缓存。该机制配合 VAD 暂停/恢复（resume_vad_detection），使打断自然流畅，是 AI 语音陪伴产品全双工体验的关键。

12.4 内容安全与输出门控

core/providers/content_safety 与 core/utils/content_safety.py 对 LLM 输出进行安全校验。系统设计了输出门控（output gate）机制：_release_gate_result、_feed_checked_output、_finish_checked_output 协同管理待输出内容的校验-释放-阻断流程。不安全内容在送入 TTS 前被拦截，保证语音陪伴产品对未成年用户的安全。门控支持按句子粒度阻断，仅截断不安全片段而不影响已正常播放的内容。

12.5 GC 管理器

语音交互产生大量临时对象（PCM 帧、Opus 包、消息体），Python 默认 GC 在长连接高并发下可能引发停顿。core/utils/gc_manager 提供独立的 GC 调度策略，在空闲期主动回收，避免在关键音频处理路径触发 GC 停顿影响实时性。gc_manager 以单例模式运行（get_gc_manager），全局统一调度。

12.6 音频速率控制

audioRateController 控制音频回传速率，匹配设备播放消费速度。若服务端产出快于设备播放，队列堆积导致延迟累积；若产出慢于播放，出现卡顿。速率控制器动态调节发送间隔，保证平滑播放。该机制对弱网场景尤为重要。

12.7 声纹识别

core/utils/voiceprint_provider 与 _initialize_voiceprint 实现说话人识别。用户首次对话登记声纹，后续对话中识别说话人身份，联动记忆与画像实现多用户区分。该能力使同一设备能服务多名家庭成员且各自保持独立记忆，是家庭场景的核心能力。

12.8 唤醒词

core/utils/wakeup_word 管理设备唤醒词配置，支持自定义唤醒词与离线唤醒。enable_wakeup_words_response_cache 开启唤醒词响应缓存，降低重复唤醒延迟。唤醒词与声纹、VAD 协同，构成设备"听到名字即响应"的低功耗待机能力。enable_greeting 控制设备唤醒后是否主动问候。

12.9 对话管理

core/utils/dialogue.py 的 Dialogue 类管理多轮对话历史，支持上下文截断（防止 token 溢出）、系统提示词注入（prompt_manager）、few-shot 工具调用示例注入（_inject_tool_call_fewshot）。对话历史是 LLM 推理与记忆召回的共同上下文。change_system_prompt 支持运行时切换角色提示词。

12.10 提示词增强

_init_prompt_enhancement 与 prompt_manager 实现系统提示词的动态增强：根据设备绑定信息、用户画像、当前时间、记忆召回结果动态拼装 system prompt，使同一 LLM 在不同用户、不同场景下产出更贴切的回复。该机制是个性化对话的核心。

12.11 输出序号管理

output_counter 统一管理输出序号，为内容安全门控与速率控制提供有序基准。每个待输出句子分配唯一序号，门控按序号阻断或释放，速率控制按序号调度发送。该设计保证在并发与中断场景下输出顺序的正确性。

12.12 退出指令与通知

exit_commands 配置退出指令词列表，handle_exit_intent 插件识别后主动结束对话。enable_stop_tts_notify 与 stop_tts_notify_voice 配置打断时的通知语音。这些细节共同打磨对话体验的边界场景。

12.13 P3 与文本工具

core/utils/p3.py 与 textUtils.py 提供文本处理工具：句子切分、标点归一化、特殊字符过滤。_clean_response_garbage 清洗模型输出的垃圾文本，_merge_tool_calls 合并去重多工具调用。这些工具保证流水线各阶段输入输出的整洁。

十三、部署与运维设计

13.1 容器化部署

系统提供 Dockerfile 与 docker-compose 配置，支持容器化部署。docker-compose-oceanbase.yml 集成 OceanBase 与依赖服务，一键拉起完整运行环境。docker-compose_all.yml 提供全量依赖部署。生产环境推荐以容器部署保证环境一致性。docker-compose.yml 提供基础部署模板。

13.2 依赖管理

依赖固定在 requirements.txt，重型 ML 依赖（torch 2.2.2、funasr 1.2.7、sherpa_onnx 1.12.29、silero_vad 6.1.0）单独标注。推荐 Python 3.12。requirements-dev.txt 提供开发期额外工具。依赖安装后需校验 ffmpeg 可执行（check_ffmpeg_installed 启动强制检查）。

13.3 启动流程

  1. app.py 入口调用 load_config 加载三层配置。
  2. setup_logging 初始化 loguru 日志。
  3. check_ffmpeg_installed 校验 ffmpeg 安装。
  4. 确定 auth_key（配置 > 智控台 secret > 随机）。
  5. 启动 SimpleHttpServer（端口 8003）。
  6. 启动 WebSocketServer（端口 8000）。
  7. 进入 wait_for_exit 等待 SIGINT/SIGTERM 优雅退出。
  8. monitor_stdin 消费回车键，支持交互式命令。

13.4 日志与监控

采用 loguru 结构化日志，config/logger.py 统一配置 log_format 与 log_format_file。audit.log 记录关键审计事件。WebSocket 连接、Provider 初始化、对话摘要、工具调用均有日志埋点，支持按 client_id 追踪全链路。日志格式含时间、版本、模块、级别、文件行号，便于定位问题。

13.5 性能基准

performance_tester/ 提供 ASR、LLM、TTS 的独立基准测试脚本，可在接入新服务商后量化首字延迟、识别准确率、合成耗时等指标，作为选型与调优依据。performance_tester.py 是统一入口。该机制保证系统在扩展能力矩阵时性能可量化、可对比。

13.6 优雅退出

wait_for_exit 通过 asyncio.Event 与信号处理器（SIGINT/SIGTERM）实现优雅退出。收到退出信号后，停止接收新连接，等待现有连接的 _save_and_close 完成，保存对话摘要，释放 Provider 资源。Windows 平台依赖 KeyboardInterrupt 冒泡。该设计保证退出不丢失对话上下文。

十四、安全设计

14.1 鉴权与加密

WebSocket 握手与 HTTP 接口均需鉴权。auth_key 作为根密钥签发 JWT，Token 带过期时间。设备密钥（client_secret）由智控台在设备注册时下发，连接时校验。密钥与敏感配置存于 data/.config.yaml（gitignore），不入版本控制。生产环境 auth_key 必须显式配置，避免随机密钥导致多实例不一致。

14.2 输入校验

对所有外部输入（WebSocket 消息、HTTP 参数、音频帧）进行校验。消息格式由 TextMessageType 枚举约束，非法类型拒绝处理。MCP 端点格式由 validate_mcp_endpoint 校验，防注入。OTA 请求校验 device_id 与 version 合法性。视觉分析请求校验图片格式与大小。

14.3 内容安全

LLM 输出经内容安全 Provider 校验，不安全内容在 TTS 前阻断。输出门控机制保证阻断不影响已正常播放的内容，仅截断后续不安全片段。该设计满足语音陪伴产品面向未成年用户的合规要求。

14.4 资源隔离

每连接独立 ConnectionHandler，独立队列与 Provider 实例，单连接异常不影响其他连接。队列有容量上限，防止恶意客户端耗尽内存。clear_queues 与 reset_audio_states 在连接异常时清理资源。各类超时（close_connection_no_voice_time、tts_timeout、tool_call_timeout）防止资源被异常连接长期占用。

14.5 OTA 安全

固件包带 MD5 校验，设备下载后验证完整性，防止固件被篡改。OTA Token 由 auth_key 签名带过期，防止未授权设备拉取固件。固件分发通过 HTTPS，保证传输安全。

14.6 密钥管理

所有密钥（LLM API Key、TTS API Key、ASR API Key、auth_key、设备密钥）均存于 data/.config.yaml 或智控台远程配置，不入代码仓库。代码中通过配置读取，不硬编码。该设计满足密钥管理与轮换的合规要求。

14.7 审计日志

audit.log 记录关键安全事件：设备认证、配置拉取、OTA 请求、内容安全阻断。审计日志独立于运行日志，用于安全事件追溯。对话摘要持久化（mem_report_only 模式）也作为业务审计的一部分。

十五、数据结构设计

15.1 音频帧结构

设备与服务端之间的音频帧为二进制 WebSocket 帧，载荷为 Opus 编码数据，附带时间戳元数据。时间戳用于 AEC 对齐与速率控制。PCM 帧在服务端内部流转，采样率 16kHz、16 位单声道，是 ASR/VAD/TTS 的统一处理格式。Opus 编解码隔离在 opus_encoder_utils，业务层只感知 PCM。

15.2 TTS 句子队列结构

tts_audio_queue 的元素为三元组 (sentence_type, opus_packets, text)，sentence_type 取 FIRST/MIDDLE/LAST。FIRST 标记一句开始，MIDDLE 标记句中续包，LAST 标记一句结束。该三态设计使 sendAudioHandle 能按句子边界有序回传，设备可逐句播放而非整段等待。

# tts_audio_queue 元素结构
(sentence_type: SentenceType,  # FIRST / MIDDLE / LAST
 opus_packets: list[bytes],    # Opus 编码包列表
 text: str | None)             # 对应文本（LAST 携带）

15.3 消息体结构

WebSocket 文本消息为 JSON，核心字段 type 标识消息类型，其余字段按类型不同。hello 消息携带设备能力、音频参数；listen 携带 state（start/stop）；iot 携带设备实体与属性；mcp 携带工具名与参数。所有消息体经 TextMessageType 枚举校验类型合法性。

# hello 消息示例
{
  "type": "hello",
  "device_id": "xxx",
  "client_id": "xxx",
  "audio_params": {
    "format": "opus",
    "sample_rate": 16000,
    "channels": 1
  }
}

15.4 对话历史结构

Dialogue 类维护对话历史为 messages 列表，每条为 {role, content} 字典。role 取 system/user/assistant/tool。系统提示词在 system 角色，用户输入在 user，LLM 回复在 assistant，工具结果在 tool。上下文截断保留首尾、裁剪中段，保证 token 不溢出且保留关键上下文。

15.5 配置数据结构

配置以嵌套 dict 表示，顶层键包括 server、selected_module、log、chat_quota、plugins、xiaozhi、context_providers、wakeup_words、mcp_endpoint 等。selected_module 的子键 ASR/TTS/LLM/VAD/Intent/Memory 为各能力的类名。三层配置递归合并为单一 dict，全局只读。

15.6 记忆存储结构

向量记忆存储为 (id, content, embedding, metadata) 四元组，embedding 为 LLM 生成的向量。知识图谱存储为 (subject, predicate, object) 三元组。两者通过 entity id 关联。用户画像为结构化 JSON，含性格、兴趣、关系等字段。所有存储由 pyobvector 客户端访问 OceanBase。

十六、异常处理设计

16.1 异常处理原则

本系统对所有外部交互（网络 IO、模型推理、工具执行）均做异常捕获与降级处理，遵循"永不因单点异常导致连接崩溃"原则。异常在最近可处理层捕获，转换为用户可理解的响应或日志记录，不向上传播导致服务退出。

16.2 Provider 异常

ASR/TTS/LLM 等 Provider 在推理失败时捕获异常，记录日志并产出降级响应（如 TTS 失败时回退默认提示音，LLM 失败时回复固定话术）。tts_timeout 与 tool_call_timeout 防止 Provider 无限阻塞。Provider 异常不中断连接，仅中断当前轮对话，下一轮自动恢复。

16.3 连接异常

WebSocket 连接断开由 handle_connection 的 try/except 捕获，触发 _save_and_close 保存对话摘要后释放资源。clear_queues 与 reset_audio_states 清理残留队列与状态。连接异常不影响其他连接，资源隔离保证系统整体稳定。

16.4 TTSException

系统定义 TTSException(RuntimeError) 专用于 TTS 合成异常。合成失败抛出 TTSException 由 chat 方法捕获，清理 TTS 队列后继续接受下一轮对话。该异常类型使 TTS 错误可与其他错误区分处理。

16.5 配额检查

_check_chat_quota 在对话前检查配额，超限则拒绝本轮对话并提示用户。chat_quota 配置段定义配额规则。该机制防止单用户过度消耗资源，保护系统整体可用性。

16.6 日志记录

所有异常均经 loguru 记录，含 client_id、异常类型、堆栈，便于按连接追踪。audit.log 单独记录安全相关异常（认证失败、内容安全阻断）。日志分级，ERROR 级以上触发告警。

十七、性能设计

17.1 首字延迟优化

首字延迟（用户说完到设备开始播放回复）是语音交互体验的核心指标。本系统通过四层优化控制延迟：流式处理（各阶段边产边消费）、句子切分（TTS 按句合成首句即播）、懒加载（Provider 按需初始化）、并发编排（ASR/LLM/TTS 协程并发）。目标首字延迟控制在秒级。

17.2 并发模型

系统基于 asyncio 单事件循环，所有 IO 与编排均为协程，避免线程切换开销。每连接独立事件流，互不阻塞。重型推理（本地 ASR/TTS/LLM）通过线程池与事件循环协同，防止阻塞主循环。_report_worker 等后台协程在空闲期执行非关键任务。

17.3 内存优化

GC 管理器在空闲期主动回收，避免在音频处理路径触发停顿。队列设容量上限防止内存膨胀。Provider 实例按 client_id 缓存复用，避免重复加载模型。Opus 包用后即释，PCM 帧处理完即丢弃。close_connection_no_voice_time 自动关闭空闲连接释放资源。

17.4 网络优化

Opus 编码低带宽传输，16kHz 单声道下约 24kbps。音频速率控制匹配设备消费速度，避免缓冲溢出。WebSocket 长连接复用，避免频繁握手。enable_websocket_ping 可选开启心跳保活，适配 NAT 超时场景。

17.5 性能基准测试

performance_tester/ 提供独立基准测试，量化各 Provider 的延迟与吞吐。ASR 测试统计识别延迟与准确率，LLM 测试统计首 token 延迟与生成速度，TTS 测试统计首音频包延迟与合成速度。测试结果作为服务商选型与参数调优的量化依据。performance_tester.py 为统一入口，支持按配置批量测试。

17.6 启动性能

Provider 懒加载使启动不等待全部模型加载，首连接到达时按需初始化。_background_initialize 在后台初始化重型 Provider，不阻塞首帧处理。该设计使系统冷启动到可服务状态时间可控。

十八、接口协议详细设计

18.1 WebSocket 握手协议

设备通过 WebSocket 连接 ws://<host>:8000/，握手时在 query 或 header 携带 JWT 或 Oauth-Token。WebSocketServer._handle_auth 校验 Token，通过后创建 ConnectionHandler 并进入 handle_connection 主循环。握手失败的连接由 _http_response 返回 401。

18.2 hello 握手消息

连接建立后设备发送 hello 消息，携带 device_id、client_id、audio_params（format、sample_rate、channels）。服务端响应 hello 确认会话建立，下发 session_id 与服务端音频参数。hello 消息由 helloHandle 处理，完成设备能力协商。

18.3 listen 监听控制

listen 消息的 state 字段控制收音：start 表示设备开始上传音频帧，stop 表示停止。服务端据此启停 ASR 流水线。该消息也用于设备主动告知"我说完了"，配合 VAD 静音判定共同确认语音段边界。

18.4 iot 设备控制协议

iot 消息携带设备实体（entity）与属性（attributes），支持上报与控制双向。设备上报状态时 from=device，服务端控制时 from=server。LLM 可通过工具调用触发 iot 控制消息，实现语音控制硬件。

18.5 OTA 接口协议

OTA 端点 /xiaozhi/ota/ 接受 GET 请求，query 参数 device_id 与 version。响应 JSON 含 version（最新版本）、size（字节数）、md5（校验和）、url（下载地址）。设备按 url 下载 .bin 文件，校验 md5 后升级。Token 通过 query 或 header 携带，由 auth_key 签名。

18.6 视觉分析接口协议

视觉端点 /mcp/vision/explain 接受 POST，body 含 image（Base64 或 URL）与可选 prompt。响应 JSON 含 description（图像描述）。JWT 在 Authorization header 携带。该端点作为 MCP 工具被对话调用，实现多模态交互。

18.7 错误响应

HTTP 错误响应统一 JSON 格式：{code, message}。code 为业务错误码，message 为人类可读说明。鉴权失败返回 401，参数错误返回 400，服务异常返回 500。错误消息不泄露敏感信息（密钥、内部路径）。

十九、设备生命周期管理设计

19.1 设备注册

设备首次接入前需在智控台完成注册，获取 device_id 与 client_secret。注册信息含设备型号、MAC 地址、归属用户。智控台将注册信息持久化并通过 manager-api 暴露给本系统校验。设备出厂后通过 OTA 绑定服务地址，首次上电即向本系统发起 WebSocket 连接完成激活。

19.2 设备激活与绑定

设备首次连接时携带 device_id 但未绑定用户，进入待绑定流程。_discard_message_with_bind_prompt 引导用户完成绑定，绑定后用户与设备建立归属关系。绑定信息由智控台管理，本系统在连接时拉取校验。已绑定设备直接进入对话流程。

19.3 连接保活

WebSocket 长连接通过 ping 消息保活（enable_websocket_ping 可选）。设备定期发送 ping，服务端响应确认存活。close_connection_no_voice_time（默认 120 秒）无语音输入即关闭连接，释放资源。连接断开后设备自动重连，本系统按 client_id 复用 Provider 实例。

19.4 设备重启

handle_restart 处理设备主动重启请求，清理当前连接状态后重新初始化。_init_connection_state 重置连接级状态，_save_and_close 保存对话摘要后关闭。重启不等同于断连，重启保留设备绑定与记忆，仅重置会话状态。

19.5 设备解绑

设备解绑由智控台发起，解除用户与设备的归属关系。解绑后设备进入待绑定流程，原有用户的记忆与画像保留但不再对该设备生效。本系统在连接时拉取最新绑定状态，智控台解绑即时生效。

19.6 固件升级

OTA 固件升级是设备生命周期的重要环节。设备请求 /xiaozhi/ota/ 获取最新固件元数据，按 url 下载 .bin，校验 md5 后升级。升级失败设备保持原版本，不影响服务。固件版本由智控台管理，支持按设备型号灰度发布。

19.7 设备状态上报

设备通过 report 消息上报运行状态：电量、网络强度、音量、温度等。reportHandle 接收，_report_worker 后台消费，_process_report 写入日志与智控台。状态数据用于运维监控与故障预警，是设备生命周期管理的数据基础。

二十、可观测性设计

20.1 日志体系

系统采用 loguru 结构化日志，config/logger.py 统一配置。log_format 含时间、版本、模块、tag、级别、文件行号、消息，便于按维度检索。log_format_file 为文件持久化格式。日志级别分 DEBUG/INFO/WARNING/ERROR/CRITICAL，生产环境默认 INFO。日志支持按 client_id 追踪单设备全链路，便于问题定位。

20.2 审计日志

audit.log 独立于运行日志，记录关键安全与业务事件：设备认证、配置拉取、OTA 请求、内容安全阻断、配额超限。审计日志不可篡改，用于安全事件追溯与合规审计。对话摘要持久化（mem_report_only 模式）也作为业务审计的一部分。

20.3 对话摘要

每轮对话结束后 _log_dialogue_summary 生成摘要，含用户输入、系统回复、工具调用、意图命中情况。摘要写入记忆系统与日志，既是记忆召回的数据源，也是对话质量分析的数据基础。摘要不记录原始音频，仅记录文本与元数据。

20.4 性能埋点

关键路径埋点统计延迟：VAD 判定延迟、ASR 识别延迟、LLM 首 token 延迟、TTS 首包延迟、首字端到端延迟。埋点数据写入日志，可聚合分析瓶颈环节。performance_tester 提供离线基准，运行时埋点提供在线指标，两者互补。

20.5 健康检查

系统可对接智控台健康检查接口，上报服务存活、Provider 可用性、连接数、队列积压等指标。智控台据此做运维告警与负载均衡。健康数据是系统可观测性的实时视图。

20.6 错误追踪

异常经 loguru 记录完整堆栈，含 client_id、异常类型、发生位置。ERROR 级以上触发告警。可对接 Sentry 等错误追踪平台（通过 loguru sink）实现错误的聚合与通知。错误追踪保证线上问题可被发现与定位。

二十一、数据流详细设计

21.1 收音数据流

设备上传 Opus 帧经 WebSocket 到达 handle_connection，_route_message 识别为二进制后调用 _process_websocket_audio。_decode_opus_packet 将 Opus 解为 PCM，_apply_aec 做回声消除，_put_asr_audio_with_aec 将 PCM 帧入 asr_audio_queue。同时 receiveAudioHandle 调用 vad.is_vad 判定语音活动，触发 ASR 开始/结束。

Opus 帧 → _process_websocket_audio → _decode_opus_packet
  → _apply_aec → _put_asr_audio_with_aec → asr_audio_queue
  → ASR Provider 流式识别

21.2 识别数据流

ASR Provider 从 asr_audio_queue 取 PCM 帧流式识别，VAD 判定静音时触发产出最终文本。文本经 handle_user_intent 意图识别：命中则直接执行工具产出响应，未命中则进入 chat 方法。识别数据流的关键是 VAD 与 ASR 的解耦协作——VAD 切段，ASR 转写。

21.3 对话数据流

chat 方法接收识别文本，构造 messages（system prompt + 对话历史 + 当前输入），调用 LLM Provider 流式生成。生成期间若触发工具调用，_handle_function_result 暂停文本送入 TTS，执行工具后结果回灌 LLM 继续生成。生成的文本流式送入 TTS Provider。

识别文本 → chat → 构造 messages
  → LLM 流式生成 → 触发工具？
    是: _handle_function_result → 回灌 → 继续生成
    否: 文本 → TTS Provider

21.4 合成数据流

TTS Provider 将 LLM 流式文本按标点切分为句子，逐句合成 Opus 包，按 FIRST/MIDDLE/LAST 标记入 tts_audio_queue。sendAudioHandle 从队列取包，按句子序号有序回传设备。audioRateController 调节回传速率匹配设备播放速度。合成数据流的关键是流式与句子切分，使首句合成完成即开始播放。

21.5 记忆数据流

对话结束后 _log_dialogue_summary 生成摘要，Memory Provider 提取记忆事实向量化存入 OceanBase，用户画像由 UserMemory 提取存入知识图谱。下一轮对话前 _initialize_memory 按当前输入召回相关记忆与画像，经 prompt_manager 增强进 system prompt。记忆数据流的双向（存入与召回）构成跨会话个性化。

21.6 工具调用数据流

LLM 决定调用工具时产出 tool_calls，UnifiedToolHandler 按工具名分发到对应执行器（device_iot/device_mcp/mcp_endpoint/server_mcp/server_plugins）。执行器执行工具，结果经 _handle_function_result 构造为 tool 消息回灌 LLM。_merge_tool_calls 合并去重多工具调用保证幂等。工具调用数据流是 LLM 能力扩展的核心。

21.7 上报数据流

设备上报状态经 reportHandle 接收，入上报队列，_report_worker 后台消费，_process_report 写入日志与智控台。上报数据流与对话数据流隔离，互不阻塞，保证上报不影响对话实时性。

二十二、扩展机制设计

22.1 Provider 扩展

新增 ASR/TTS/LLM/VAD/Intent/Memory 服务商的步骤：在 core/providers/<能力>/ 下新增实现文件，实现继承基类的类，在 data/.config.yaml 或智控台 selected_module 配置类名。工厂函数 create_instance 动态导入并实例化，无需改业务代码。该机制使能力矩阵可持续扩展，目前已支持 ASR 14 家、TTS 20 家、LLM 11 家。

22.2 函数插件扩展

新增工具能力的步骤：在 plugins_func/functions/ 下新增模块，实现 BaseFunction 子类并用 @register_function(name, desc, type) 装饰。loadplugins.auto_import_modules 启动时自动扫描注册，LLM 即可调用。该机制使工具能力可由开发者独立扩展，目前已内置 15 个插件。

22.3 消息类型扩展

新增 WebSocket 消息类型的步骤：在 textMessageType 枚举增加成员，在 textHandler 下新增处理器，在 TextMessageHandlerRegistry 注册分发。新类型立即对设备可用，不影响既有类型处理。该机制使设备协议可持续演进。

22.4 上下文源扩展

context_providers 配置支持注入外部上下文。新增上下文源只需实现接口并在配置声明，对话前自动拉取注入 system prompt。该机制使系统能接入业务系统数据（如设备状态、环境信息）作为对话上下文。

22.5 MCP 工具扩展

MCP 协议支持动态接入第三方工具集。在配置声明 MCP 端点，validate_mcp_endpoint 校验后，端点暴露的工具自动纳入 UnifiedToolHandler 对 LLM 可用。该机制使系统能接入广泛的 MCP 生态工具而不改动核心代码。

22.6 开闭原则

上述四类扩展（Provider、插件、消息、上下文）均遵循开闭原则：对扩展开放（新增实现类/模块/枚举），对修改关闭（不改工厂、调度器、分发器核心逻辑）。该设计保证系统在功能持续扩展的同时核心稳定，降低维护成本与回归风险。

二十三、容量与配额设计

23.1 对话配额

chat_quota 配置段定义对话配额规则，_check_chat_quota 在每轮对话前检查。配额可按用户、按设备、按时间段限制对话次数或 token 消耗，防止单用户过度占用资源。超限拒绝本轮对话并提示用户。该机制是系统多租户资源公平的基础。

23.2 连接数控制

系统支持并发多连接，每连接独立 ConnectionHandler。连接数受服务端资源（内存、文件描述符）约束。close_connection_no_voice_time 自动关闭空闲连接释放资源。生产环境通过多实例部署与负载均衡承载更高并发。

23.3 队列容量

asr_audio_queue 与 tts_audio_queue 设容量上限，防止异常客户端或慢消费导致内存膨胀。队列满时丢弃最旧帧（音频实时性高于完整性）或阻塞生产者（视队列语义而定）。该设计保证系统在异常输入下的内存安全。

23.4 超时保护

三类超时共同保护资源不被异常占用：close_connection_no_voice_time（120s 无语音关闭连接）、tts_timeout（10s TTS 合成超时）、tool_call_timeout（30s 工具调用超时）。超时触发清理与降级，保证系统在异常 Provider 或恶意客户端下的稳定。

23.5 delete_audio 配置

delete_audio 配置控制是否在处理后删除临时音频文件，平衡磁盘占用与可追溯性。生产环境通常开启以控制磁盘，调试期可关闭以保留样本。该配置体现系统对资源占用的细粒度控制。

23.6 资源隔离

每连接独立队列与 Provider 实例，单连接异常（队列堆积、Provider 崩溃）不扩散至其他连接。连接级资源在 close 时统一清理。该隔离保证系统整体可用性不受单连接异常影响，是多租户安全的关键。

二十四、插件系统详细设计

24.1 插件架构

plugins_func/ 是系统的工具能力扩展层，由 loadplugins.py、register.py 与 functions/ 三部分构成。loadplugins.auto_import_modules("plugins_func.functions") 在启动时动态扫描 functions/ 目录下所有 .py 模块并导入，触发模块级的 @register_function 装饰器执行，将能力注册至全局注册表。该设计实现零配置发现——新增插件只需新增文件。

24.2 注册机制

@register_function(name, desc, type) 装饰器接收三个参数：name 为工具唯一标识（LLM 据此调用），desc 为自然语言描述（LLM 据此理解工具用途），type 为 ToolType 枚举（SYS_PLAYER/SENSOR 等，用于分类与权限）。装饰器将被装饰类的引用存入全局注册表，UnifiedToolHandler 启动时从注册表加载全部工具对 LLM 暴露。

@register_function(name="get_weather", desc="查询指定城市天气",
                   type=ToolType.SENSOR)
class GetWeatherFunction(BaseFunction):
    async def execute(self, city: str, **kwargs):
        # 调用天气 API，返回结构化结果
        return {"city": city, "weather": "...", "temp": "..."}

24.3 插件基类

所有插件继承 BaseFunction，实现 execute 方法。execute 接收关键字参数（由 LLM 从工具调用参数映射），返回结构化结果。结果经 _handle_function_result 回灌 LLM，LLM 据此生成自然语言回复。BaseFunction 提供日志、异常捕获、配额检查的通用支撑，插件只需关注业务逻辑。

24.4 插件配置

各插件可在 config.yaml 的 plugins 段配置独立参数：get_weather 的 api_key、get_news 的 url 列表、search_from_ragflow 的接口地址与 key、web_search 的搜索引擎选择。插件在 execute 时读取配置，配置缺失则降级或提示。该设计使插件能力可运维化调整而无需改代码。

24.5 Home Assistant 集成

系统提供 hass_init、hass_get_state、hass_set_state、hass_play_music 四个插件对接 Home Assistant 智能家居平台。hass_init 初始化连接，get/set_state 读写设备状态，play_music 通过 HA 控制媒体播放器。该集成使本系统能作为语音中枢控制 HA 生态设备，扩展了智能家居场景能力。

24.6 退出与角色插件

handle_exit_intent 插件识别退出指令（exit_commands 配置），主动结束对话。change_role 插件支持运行时切换智能体角色（change_system_prompt）。call_device 插件支持呼叫其他设备。这些插件覆盖了对话控制的边界场景，使系统能响应用户的元指令（退出、换角色）而非仅业务问答。

24.7 知识库与搜索插件

search_from_ragflow 插件对接 RAGFlow 知识库，支持私有知识检索增强生成。web_search 插件支持联网搜索（多搜索引擎可选），使 LLM 能获取实时信息。两个插件分别覆盖私有知识与公网信息两个维度，是 RAG（检索增强生成）能力的实现基础。

二十五、会话管理设计

25.1 会话标识

每个 WebSocket 连接对应一个独立会话，由 client_id 唯一标识。会话状态封装在 ConnectionHandler 实例中，包括对话历史（Dialogue）、Provider 实例、队列、认证态。会话与设备多对一：同一设备断连重连视为新会话，但按 client_id 复用 Provider 与记忆，保证体验连续。

25.2 对话上下文

Dialogue 类管理多轮对话上下文，维护 messages 列表。上下文截断策略保留首条 system prompt 与最近若干轮，裁剪中段历史，防止 token 溢出。_inject_tool_call_fewshot 在上下文注入工具调用示例，提升 LLM 工具调用准确率。prompt_manager 与 _init_prompt_enhancement 动态增强 system prompt，注入用户画像、记忆召回、当前时间等。

25.3 会话恢复

设备断连重连后，本系统按 client_id 复用已初始化的 Provider 实例，避免重复加载模型。对话历史从记忆系统召回最近摘要重建上下文，使会话在断连后仍能保持上下文连续。该设计保证网络抖动下的体验连续性。

25.4 多用户会话

声纹识别使同一设备能区分多用户会话。不同说话人对应不同的记忆与画像，_initialize_memory 按声纹识别结果加载对应用户的记忆。该设计支持家庭场景——同一设备服务多名家庭成员，各自独立记忆与画像，互不干扰。

25.5 会话终止

会话终止触发 _save_and_close：生成对话摘要写入记忆系统，清理队列与状态，释放 Provider 引用（不销毁实例以便复用）。终止可由设备主动（close 消息）、超时（无语音超时）或异常（连接断开）触发。终止后设备可重连开启新会话。

25.6 问候与唤醒

enable_greeting 控制设备唤醒后是否主动问候。问候语由智能体角色配置决定，经 TTS 合成播放。唤醒词响应缓存（enable_wakeup_words_response_cache）缓存常见唤醒词的响应，降低重复唤醒延迟。问候与唤醒是会话起始的用户体验细节。

二十六、设备能力协商设计

26.1 能力协商协议

设备在 hello 握手消息中声明自身能力：音频参数（format、sample_rate、channels）、支持的 IoT 实体、唤醒词。服务端据此协商后续交互参数。协商结果在 hello 响应中回传设备，双方按协商结果通信。该机制保证异构设备（不同硬件能力）能接入同一服务端。

26.2 音频参数协商

设备声明支持的音频格式与采样率，服务端选择双方支持的参数。默认 Opus 16kHz 单声道。若设备不支持 Opus，服务端可降级为 PCM 或其他编码。协商结果影响 Opus 编解码参数与 ASR/TTS 的采样率配置。

26.3 IoT 实体协商

设备声明拥有的 IoT 实体（传感器、开关、灯等），服务端据此注册可控制设备列表。LLM 通过工具调用控制这些实体。设备能力变化时通过 iot 消息上报更新。该协商使 LLM 只感知设备实际拥有的能力，避免无效控制指令。

26.4 唤醒词协商

设备声明支持的唤醒词，服务端在 wakeup_words 配置中匹配。唤醒词用于设备本地唤醒，触发后建立连接进入会话。自定义唤醒词通过智控台下发给设备。唤醒词是设备"听到名字即响应"的触发条件。

26.5 OTA 地址下发

设备首次连接时，服务端在 OTA 响应中下发 WebSocket 地址与 MQTT 网关配置，使设备出厂后绑定服务地址。该机制使设备无需预置服务地址，支持出厂后动态绑定与迁移。mqtt_gateway 与 UDP 网关配置也通过 OTA 下发。

二十七、模型管理设计

27.1 模型文件管理

本地推理模型（如 SenseVoiceSmall ASR 模型）存放于 models/ 目录。模型文件不入版本控制（体积大），由部署时下载或挂载。模型路径在 Provider 配置中声明，加载时按路径读取。该设计使模型可独立于代码更新。

27.2 模型懒加载

本地模型加载耗时较长，系统通过 _background_initialize 在后台协程加载，不阻塞首帧处理。加载完成后 Provider 实例按 client_id 缓存复用。首次连接的模型加载延迟由性能基准量化，是冷启动优化的重点。

27.3 模型切换

切换模型只需修改 selected_module 配置的类名，工厂函数动态导入新实现。云端模型切换只需改 API Key 与 endpoint 配置。智控台远程配置使模型切换无需重启本系统。该设计支持 A/B 测试与服务商灰度迁移。

27.4 system_prompt 管理

core/providers/llm/system_prompt.py 提供系统提示词的动态管理。智能体角色的提示词由智控台配置下发，运行时可切换（change_system_prompt）。_init_prompt_enhancement 在基础提示词上叠加用户画像、记忆召回、当前时间等增强信息，使同一智能体在不同用户/场景下表现差异化。

27.5 多模态模型

vllm Provider（core/providers/vllm）支持本地多模态推理，用于视觉分析端点的图像理解。qwen3_asr_flash 等多模态 ASR 支持语音+视觉联合理解。多模态能力扩展了系统 beyond 纯语音的交互边界。

二十八、版本与兼容性设计

28.1 软件版本

本系统版本 V1.0。版本号在日志格式中嵌入（log_format 的 version 字段），便于运行时识别部署版本。版本管理遵循语义化版本，主版本号变更表示不兼容的架构调整。

28.2 设备固件兼容

OTA 端点按设备型号下发对应固件，支持多型号并存。固件版本号在 OTA 响应中返回，设备校验版本号决定是否升级。本系统兼容多版本固件设备同时接入，消息处理按设备能力协商结果适配。

28.3 配置兼容

config.yaml 随版本演进新增配置项，旧 data/.config.yaml 缺失的键由 config.yaml 默认值补齐（递归合并）。该设计保证配置文件跨版本兼容，升级不破坏既有本地配置。

28.4 协议兼容

WebSocket 消息协议通过 TextMessageType 枚举约束，新增类型不影响旧设备（旧设备不发送新类型，服务端忽略未知类型或回退默认处理）。该前向兼容设计使设备固件与服务端可独立演进。

28.5 上游同步

本系统基于上游 xiaozhi-esp32-server 二次开发，上游 MIT 协议允许修改与分发。本系统在上游基础上新增独创代码，新增代码著作权归属上海爱予慧。上游 LICENSE 随发行物保留，符合 MIT 要求。本系统不回吐上游，保持独立演进。

二十九、MQTT 网关集成设计

29.1 网关架构

除 WebSocket 直连外，系统支持通过 MQTT 网关接入设备。mqtt-gateway 作为桥接层，将局域网设备的 MQTT/UDP 协议转换为服务端可处理的格式。该设计覆盖非 WebSocket 组网场景，如经网关转发的局域网设备或受限网络环境。网关与设备协议由 mqtt_gateway 的 .env 配置，格式为 host:port。

29.2 MQTT 音频桥接

_process_mqtt_audio_message 处理来自 MQTT 通道的音频消息，与 WebSocket 音频统一汇入 _put_asr_audio_with_aec 进入 ASR 流水线。该设计保证无论设备经何种通道接入，下游处理一致。MQTT 签名密钥用于生成 MQTT 连接密码，保证网关接入鉴权。

29.3 UDP 网关

系统支持 UDP 网关配置，用于低延迟或受限协议场景。UDP 网关同样经 mqtt-gateway 桥接转换。网关配置通过 OTA 下发设备，使设备出厂后绑定网关地址。多网关支持使系统能适配复杂网络拓扑。

29.4 网关鉴权

MQTT 网关接入需鉴权，签名密钥由 mqtt_gateway 的 .env 配置。服务端校验网关消息的签名合法性，拒绝未授权网关。该机制保证网关接入安全，防止恶意网关注入伪造音频。

三十、内容安全详细设计

30.1 安全分层

系统内容安全分输入侧与输出侧两层。输入侧：用户语音识别文本在进入 LLM 前不做内容过滤（保留用户表达自由），但对话摘要写入记忆时可经安全过滤。输出侧：LLM 生成的文本在送入 TTS 前经内容安全 Provider 校验，不安全内容阻断。该分层平衡了表达自由与输出安全。

30.2 输出门控机制

输出门控（output gate）是本系统的独创安全机制。_release_gate_result、_feed_checked_output、_finish_checked_output 三方法协同管理待输出内容的校验-释放-阻断流程。LLM 流式产出的文本先进入门控缓冲，经安全校验通过后释放至 TTS；不安全片段在门控截断，不影响已释放并播放的内容。该设计实现按句子粒度的精准阻断。

LLM 流式文本 → _feed_checked_output(进入门控缓冲)
  → 内容安全校验
    通过 → _release_gate_result(释放至 TTS)
    不通过 → 截断该句，继续下一句
  → _finish_checked_output(本轮结束)

30.3 内容安全 Provider

core/providers/content_safety 与 core/utils/content_safety.py 实现安全校验。支持基于关键词、基于分类模型、基于 LLM 判断的多种策略。校验结果含是否安全与不安全原因，用于日志与审计。Provider 可按配置切换策略，适配不同合规要求。

30.4 安全审计

所有内容安全阻断事件写入 audit.log，含 client_id、阻断内容、阻断原因、时间。审计日志用于合规追溯与策略调优。阻断不向用户暴露原始判定细节，仅以中性话术回退，避免提示用户绕过。

30.5 边界场景

safety_context 在 chat 方法中传递安全上下文，记录当前对话的安全相关状态（如已阻断次数）。output_gate 参数允许调用方指定自定义门控策略。_log_dialogue_summary 在摘要中标注安全事件，使记忆召回时感知历史安全上下文。这些边界设计保证安全机制与对话流程的深度集成。

三十一、部署架构设计

31.1 单实例部署

开发与小规模生产采用单实例部署：一个 app.py 进程同时承载 WebSocket（8000）与 HTTP（8003）双服务，OceanBase 与 Redis 通过 docker-compose-oceanbase.yml 拉起。该部署适合中小规模（百级并发连接），资源占用低，运维简单。

31.2 多实例部署

大规模生产采用多实例部署：多个 app.py 进程经负载均衡分发 WebSocket 连接，OceanBase 与 Redis 独立集群。由于连接状态在进程内（ConnectionHandler），负载均衡需按 client_id 会话保持（sticky session），保证设备重连命中同一实例复用 Provider。HTTP 服务无状态可任意分发。

31.3 容器编排

Dockerfile 定义镜像构建，docker-compose 编排服务。生产环境推荐 Kubernetes 编排，支持滚动更新与自愈。镜像分层：基础 Python 镜像 + 依赖层 + 代码层，依赖层缓存加速构建。重型 ML 依赖（torch/funasr）单独分层，利用缓存。

31.4 数据层部署

OceanBase 作为记忆向量与图谱存储，生产环境独立部署或集群。OceanBase 兼容 MySQL，通过 pyobvector 客户端访问。Redis 作为缓存，存储热配置与连接态。数据层与应用层分离，支持独立扩缩容与备份。

31.5 网络部署

WebSocket（8000）与 HTTP（8003）对外暴露，经反向代理（nginx）终结 TLS 与负载均衡。内部 OceanBase、Redis、智控台通信走内网。mqtt-gateway 独立部署于设备侧网络，桥接局域网设备。网络分层保证对外仅暴露必要端口。

31.6 配置管理

生产环境配置通过智控台远程下发，data/.config.yaml 仅存 manager-api.url 与最小本地配置。该设计使多实例配置一致，运维集中化。配置变更通过智控台操作，本系统运行时拉取生效，无需逐实例重启。

三十二、灾备与高可用设计

32.1 无状态服务

WebSocket 与 HTTP 服务本身无状态（连接态在进程内但不跨实例共享），任一实例故障不影响其他实例。负载均衡健康检查自动剔除故障实例，新连接路由至健康实例。该设计保证服务层高可用。

32.2 记忆数据持久化

记忆与图谱存储于 OceanBase，对话摘要持久化。即使服务实例全部故障，记忆数据不丢失，恢复后可重建上下文。OceanBase 自身支持高可用部署（多副本）。该设计保证用户长期记忆的安全。

32.3 Provider 降级

单一 Provider 故障（如某云 ASR 不可用）不导致服务中断——可切换至备用 Provider（修改 selected_module）。多服务商矩阵（ASR 14 家、TTS 20 家、LLM 11 家）提供充分冗余，任一服务商故障可快速切换。该设计是服务可用性的能力层保障。

32.4 优雅退出与恢复

实例退出时 wait_for_exit 保证现有连接 _save_and_close 完成，不丢失对话摘要。实例恢复后按 client_id 复用记忆与 Provider，设备重连即恢复服务。该设计保证计划内运维（如升级）的用户无感。

32.5 超时保护

三类超时（无语音关闭、TTS 超时、工具调用超时）防止异常连接或 Provider 阻塞导致资源耗尽。即使发生故障（如 LLM 服务卡死），超时机制保证系统不无限等待，自动降级恢复。该设计是故障隔离的底层保障。

三十三、数据隐私设计

33.1 音频数据处理

用户音频在服务端以 PCM/Opus 形式临时处理，处理后即丢弃（delete_audio 控制是否留存临时文件）。音频不入版本控制、不持久化长期存储。识别文本进入对话历史与记忆，但原始音频不保留。该设计最小化音频数据留存，符合隐私最小化原则。

33.2 记忆数据隔离

记忆与画像按 client_id（设备）与声纹（用户）隔离存储。不同设备、不同用户的记忆互不可见。_initialize_memory 按当前用户身份加载对应记忆，绝不跨用户召回。该隔离保证多用户场景下的隐私边界。

33.3 对话摘要脱敏

_log_dialogue_summary 生成的对话摘要写入记忆与日志。摘要为文本元数据，不含原始音频。敏感信息（如密钥、身份证号）在摘要中不刻意保留，依赖 LLM 生成自然摘要的特性。审计日志记录阻断事件但不暴露原始不安全内容细节。

33.4 密钥与凭证

所有密钥（API Key、auth_key、设备密钥）存于 data/.config.yaml 或智控台远程配置，不入代码仓库与版本控制。日志不记录密钥明文。该设计保证凭证安全，符合密钥管理合规要求。

33.5 传输安全

WebSocket 与 HTTP 对外经反向代理终结 TLS，保证传输加密。OTA 固件通过 HTTPS 下载。内部服务间通信走内网。该设计保证数据传输的机密性与完整性。

33.6 用户数据权利

用户可通过智控台管理对话记忆与画像数据（查看、导出、删除）。设备解绑后用户记忆保留但不再对该设备生效。该设计支持用户对自身数据的管理权利，符合数据保护要求。

三十四、运维自动化设计

34.1 配置自动化

智控台集中管理智能体配置、模型参数、设备注册，本系统运行时自动拉取生效。运维人员无需登录服务器修改配置文件，全部通过智控台操作。该设计降低运维成本与人为错误风险，实现配置即代码。

34.2 日志集中化

loguru 日志可对接集中化日志平台（通过 sink）。日志含 client_id、版本、模块等结构化字段，便于按维度检索分析。错误日志可对接告警平台实现自动通知。该设计支持大规模部署下的可观测性。

34.3 健康监控

系统可对接智控台健康检查，上报服务存活、连接数、队列积压、Provider 可用性。智控台据此做告警与负载均衡决策。健康数据是运维自动化的实时输入。

34.4 容器编排运维

容器化部署支持滚动更新（零停机升级）与自愈（故障实例自动重启）。镜像分层与依赖缓存加速构建发布。该设计使部署运维标准化、自动化，降低人为干预。

34.5 性能基准自动化

performance_tester 可纳入 CI/CD 流水线，在接入新 Provider 或配置变更后自动运行基准测试，对比指标变化。该机制使性能回归可被自动发现，保证演进中的性能可控。

34.6 OTA 灰度发布

固件 OTA 支持按设备型号灰度发布，逐步放量升级。灰度发布降低固件缺陷的全局影响，支持回滚。该设计使设备固件演进的风险可控。

三十五、数字人集成设计

35.1 数字人定位

本系统可与 digital-human（数字人）项目集成，模拟 ESP32 终端设备用于测试与演示。数字人通过 WebSocket 连接本系统，复用完整语音交互流水线。该集成使开发期可在无实体设备情况下验证服务端逻辑，降低测试门槛。

35.2 测试入口

test/ 目录提供基于浏览器的 WebSocket 测试页面，可手动触发对话、上传音频、查看识别与合成结果。该入口是开发期调试的主要手段，支持快速验证流水线各环节。数字人与浏览器测试页共同构成无设备测试矩阵。

35.3 演示场景

数字人可承载视觉表现（口型、表情）同步语音输出，用于产品演示。本系统提供语音交互后端能力，数字人提供前端表现，两者经 WebSocket 解耦协作。该集成使演示场景无需 ESP32 实体硬件即可展现完整产品体验。

35.4 协议复用

数字人与实体设备复用同一 WebSocket 协议与消息类型，使本系统无需区分终端类型即可服务。该设计保证测试终端与生产终端的协议一致，测试结论可迁移至生产。

三十六、系统初始化设计

36.1 初始化序列

app.py 启动初始化严格按依赖顺序执行：setup_logging 先就绪保证后续日志可记录；load_config 加载三层配置供后续模块读取；check_ffmpeg_installed 校验音频编解码依赖；确定 auth_key 供鉴权用；启动 SimpleHttpServer 与 WebSocketServer；进入 wait_for_exit 主循环。序列保证每步前置依赖已就绪，避免初始化竞态。

36.2 Provider 懒初始化

Provider 不在启动时初始化，而在首连接由 _initialize_components 按需创建。_background_initialize 协程在后台初始化重型 Provider（如本地 ASR 模型加载），不阻塞首帧处理。modules_initialize.py 是统一初始化入口，按依赖顺序（VAD→ASR→LLM→TTS→Intent→Memory）初始化各能力。该设计使冷启动到可服务时间可控。

36.3 连接级初始化

每连接建立后执行连接级初始化：_initialize_components 创建 Provider 实例（或复用缓存）、_initialize_memory 加载记忆、_initialize_intent 初始化意图、_init_prompt_enhancement 增强提示词、_inject_tool_call_fewshot 注入工具示例。_init_connection_state 重置连接态。这些初始化使连接就绪可对话。

36.4 报告线程初始化

_init_report_threads 初始化上报相关后台协程，包括 _report_worker 消费上报队列、_check_timeout 检测超时连接、_check_aec_cache_expiry 清理 AEC 缓存。这些后台协程与主对话流程并发，互不阻塞，共同维护连接健康。

36.5 失败处理

初始化失败（如配置缺失、依赖未装、模型未下载）以明确错误信息提示并终止启动，避免带病运行。check_ffmpeg_installed 失败直接退出。Provider 类名非法由工厂抛 ImportError。fail-fast 设计保证系统只在健康状态下服务。

三十七、系统初始化与运行时协同设计

37.1 启动期与运行时协同

启动期完成无依赖可执行的初始化（日志、配置、依赖校验、双服务启动），运行期按需完成重依赖初始化（Provider 懒加载、记忆召回）。该划分使启动快速（秒级），重初始化延后到首连接或后台，不阻塞服务就绪。update_config 在运行期支持重新拉取配置，实现热更新。

37.2 后台协程与主循环

主事件循环承载 WebSocket 与 HTTP 服务的连接处理，后台协程（_background_initialize、_report_worker、_check_timeout、_check_aec_cache_expiry、monitor_stdin）并发运行不阻塞主循环。协程间通过共享状态（ConnectionHandler）与队列协作。该设计是 asyncio 单循环并发模型的核心。

37.3 信号处理

wait_for_exit 注册 SIGINT/SIGTERM 信号处理器，设置 stop_event 触发优雅退出。退出时停止接受新连接，等待现有连接 _save_and_close，保存对话摘要，释放资源。Windows 依赖 KeyboardInterrupt 冒泡。该设计支持容器编排的优雅终止信号（SIGTERM）。

37.4 monitor_stdin

monitor_stdin 协程消费标准输入回车键，支持交互式运维命令（如手动触发配置重载）。该通道是开发期与运维期的手动干预入口，与信号通道互补。

37.5 GC 调度协同

gc_manager 以单例运行，在主循环空闲期调度 GC，避免在音频处理关键路径触发停顿。GC 调度与对话流程协同，感知系统负载动态调节。该协同是实时性优化的底层保障。

三十九、接口适配层设计

39.1 HTTP 处理器基类

core/api/base_handler.py 定义 HTTP 处理的通用基类，封装鉴权、参数校验、异常捕获、响应构造的公共逻辑。OtaHandler 与 VisionHandler 继承基类，仅实现业务逻辑。该设计消除 HTTP 处理器的重复代码，保证鉴权与响应格式一致性。

39.2 鉴权适配

HTTP 处理器经 base_handler 统一调用 core/auth 完成 JWT 校验。鉴权失败返回 401 统一格式。OTA Token 与视觉 JWT 共用 auth_key 根密钥但签名载荷不同，base_handler 按 endpoint 区分校验逻辑。该适配使鉴权集中可维护。

39.3 响应封装

所有 HTTP 响应经 base_handler 统一封装为 JSON 格式，含成功标志、数据载荷、错误信息。成功响应 200，参数错误 400，鉴权失败 401，服务异常 500。响应不泄露敏感信息（内部路径、密钥、堆栈）。该封装保证接口风格一致，便于客户端处理。

39.4 异常适配

base_handler 捕获处理器抛出的全部异常，转换为错误响应而非 500 崩溃。业务异常记日志后返回 4xx，系统异常记日志后返回 5xx。该适配保证单个请求异常不影响服务整体可用性，是 HTTP 服务健壮性的保障。

四十、错误分类与恢复设计

40.1 错误分类

系统错误分四类：配置错误（启动期，fail-fast 终止）、网络错误（IO，重试或降级）、Provider 错误（推理失败，降级响应）、协议错误（消息非法，拒绝处理）。每类有对应处理策略，不混用。该分类使错误处理有的放矢。

40.2 可恢复错误

网络错误与 Provider 错误为可恢复错误，捕获后降级处理：TTS 失败回退默认提示音，LLM 失败回复固定话术，ASR 失败提示重新输入。降级不中断连接，下一轮对话自动恢复原流程。该策略保证用户体验连续。

40.3 不可恢复错误

配置错误为不可恢复错误，启动期 fail-fast 终止避免带病运行。auth_key 缺失、ffmpeg 未装、Provider 类名非法均属此类。错误信息明确指向缺失项，便于运维快速修复。该策略保证系统只在健康态服务。

40.4 连接级恢复

单连接异常（队列堆积、Provider 崩溃）由该连接的 ConnectionHandler 捕获，clear_queues 与 reset_audio_states 清理后恢复就绪。不影响其他连接。close 在异常不可恢复时保存摘要后关闭，设备重连开启新会话。该设计是资源隔离的恢复保障。

40.5 错误日志与可追溯

所有错误经 loguru 记录完整上下文：client_id、错误类型、堆栈、发生位置。ERROR 级以上可触发告警。错误日志支持按 client_id 追溯单设备全链路问题，是线上运维的定位依据。audit.log 单独记录安全相关错误。

四十四、存储与数据库设计

44.1 存储分层

系统存储分三层：OceanBase（MySQL 兼容）承载记忆向量与知识图谱，Redis 承载热配置与连接态缓存，本地文件系统承载临时音频与模型文件。三层各司其职，OceanBase 保证持久化，Redis 保证低延迟，文件系统承载大对象。存储分层平衡了持久性、性能与成本。

44.2 OceanBase 向量存储

记忆向量存储于 OceanBase 的向量列，由 pyobvector 客户端访问。每条记忆记录含 id、content、embedding、metadata 四字段。embedding 由 LLM 生成，维度依模型而定。召回时按余弦相似度检索 top-k，注入对话上下文。oceanbase_vector.py 封装向量读写。

44.3 OceanBase 图谱存储

知识图谱存储为 (subject, predicate, object) 三元组，节点为实体，边为关系。图谱支持关系查询与推理，与向量库协同——向量负责语义相似召回，图谱负责关系推理。oceanbase_graph.py 封装图谱读写。用户画像作为结构化实体存入图谱。

44.4 Redis 缓存

Redis 缓存热配置、连接态、唤醒词响应等高频访问数据。enable_wakeup_words_response_cache 开启唤醒词响应缓存，降低重复唤醒延迟。Redis 减轻 OceanBase 读压力，提升热路径响应速度。缓存设 TTL 保证最终一致。

44.5 本地文件存储

models/ 目录承载本地推理模型文件（如 SenseVoiceSmall）。临时音频文件由 delete_audio 控制是否留存。配置文件 config.yaml 与 data/.config.yaml 在文件系统。本地存储不入版本控制（模型大、配置含密钥）。

44.6 数据生命周期

对话摘要与记忆长期持久化（用户数据权利支持删除）。临时音频处理后即弃。AEC 缓存定期清理。日志按策略滚动。close_connection_no_voice_time 自动关闭空闲连接释放资源。数据生命周期管理保证存储不无限膨胀。

四十五、系统依赖与外部服务设计

45.1 依赖清单

系统依赖分四类：运行时依赖（websockets、aiohttp、aioconsole、PyJWT）、ML 推理依赖（torch、funasr、sherpa_onnx、silero_vad）、存储依赖（pyobvector、Redis 客户端）、工具依赖（loguru、PyYAML）。依赖固定于 requirements.txt，重型 ML 依赖单独标注。Python 3.12 推荐。

45.2 外部服务依赖

系统运行依赖外部服务：OceanBase（记忆存储）、Redis（缓存）、智控台 manager-api（远程配置与设备注册）、各 AI 服务商 API（ASR/TTS/LLM）、ffmpeg（音频编解码）。任一外部服务不可用时系统降级而非崩溃——AI 服务商故障可切换，智控台不可用回退本地配置，OceanBase 不可用降级无记忆模式。

45.3 智控台对接

智控台 manager-api 是本系统的核心外部依赖，提供远程配置下发与设备注册校验。manager-api.url 在 data/.config.yaml 配置，启动时拉取配置覆盖本地，运行时 update_config 支持热更新。设备认证经智控台校验 client_secret。智控台不可用时回退本地配置与离线认证。

45.4 AI 服务商对接

ASR/TTS/LLM 服务商通过 Provider 接口对接，各服务商 API Key 在 data/.config.yaml 或智控台配置。服务商故障由 Provider 异常捕获降级处理，可经智控台切换 selected_module 类名快速换服务商。多服务商矩阵提供充分冗余。

45.5 ffmpeg 依赖

ffmpeg 是音频 Opus 编解码的外部进程依赖，check_ffmpeg_installed 启动时强制校验，缺失则终止启动。编解码通过子进程调用 ffmpeg，避免阻塞事件循环。ffmpeg 是系统运行的硬依赖。

四十六、编码与设计规范

46.1 代码组织

系统代码按职责分层组织：core/ 承载核心逻辑（连接、服务、处理器、Provider、工具），config/ 承载配置与日志，plugins_func/ 承载函数插件，models/ 承载本地模型。每层高内聚低耦合，层间经抽象接口协作。代码组织遵循多小文件原则，单文件聚焦单一职责。

46.2 命名规范

Python 模块与文件用 snake_case（receiveAudioHandle 等历史命名除外），类用 PascalCase（ConnectionHandler、UnifiedToolHandler），函数与方法用 snake_case，常量用 UPPER_SNAKE_CASE。Provider 类名与服务商关联（AliyunASR、TencentTTS）。配置键用 UPPER（ASR、TTS、LLM）。

46.3 异步规范

系统全面异步，IO 与编排均为 asyncio 协程。IO 密集操作（网络、文件）用 async/await，CPU 密集操作（模型推理）经线程池协作避免阻塞事件循环。asyncio Queue 衔接流水线各阶段。每连接独立事件流，互不阻塞。

46.4 错误处理规范

外部交互均做异常捕获与降级，遵循永不因单点异常导致连接崩溃原则。异常在最近可处理层捕获，转为用户可理解响应或日志。TTSException 等自定义异常区分错误类型。fail-fast 用于启动期配置错误，运行期错误降级不中断。

46.5 配置规范

配置全部经 config_loader 三层合并读取，不硬编码。密钥存 data/.config.yaml（gitignore）或智控台远程。配置键在 config.yaml 有注释说明默认值。新增配置项随版本演进，旧配置由默认值补齐保证兼容。

46.6 文档与注释规范

关键模块（ConnectionHandler、Provider 基类、UnifiedToolHandler）有 docstring 说明职责。复杂业务规则（AEC 对齐、输出门控、句子切分）有行内注释说明原因。本设计说明书是系统级设计文档，与代码注释互补，共同保证可维护性。
